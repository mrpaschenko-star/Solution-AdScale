# API Gateway для DSP-интеграции

## 1. Решение: региональный Envoy

Использовать Envoy как специализированный DSP gateway: TLS/mTLS, доверенная identity партнёра, маршрутизация, локальные лимиты, ограничения ресурсов, outlier detection и метрики. Это тот же региональный RTB ingress из задания 1. Дополнительный gateway между ним и Bidding не ставится.

Management API Gateway остаётся отдельным входом кабинета. Его авторизация пользователей, CRUD, отчёты и длинные запросы не должны конкурировать с RTB за те же очереди и пулы. Сервис уведомлений также имеет отдельный listener/пул ingress: его ожидание durable Kafka ACK не входит в 80 мс аукциона.

| Альтернатива | Оценка |
|---|---|
| **Envoy** | Выбран: upstream limits, HTTP/2, mTLS, наблюдаемость и динамическая конфигурация подходят для RTB; требует владельца конфигурации |
| NGINX / HAProxy | Подходят для простого L7; существующее решение можно сохранить, если оно закрывает те же требования и подтверждено тестом. В кейсе оно не задано |
| Kong / универсальный API-management слой | Полезен для публичного CRUD, но плагины/синхронные вызовы авторизации не нужны на каждом аукционе; добавляет эксплуатационные компоненты |
| Только ingress в приложении | Минимум инфраструктуры, но каждой версии Bidding пришлось бы отдельно реализовывать внешнюю защиту, routing и traffic policy |

Не требуется service mesh или Kubernetes ради gateway. В трёхмесячном этапе Envoy и Bidding можно развёртывать контейнерами/сервисами на текущей инфраструктуре с CI/CD. Версия Envoy фиксируется на поддерживаемом релизе при реализации; ссылки ниже описывают механизмы, а не выбранный production build.

## 2. Маршруты и границы доверия

| Внешний маршрут | Куда направляется | Политика |
|---|---|---|
| `POST rtb.adscale.example/openrtb2/auction` | Кластер Bidding конкретного региона и стабильной release-когорты | Только аутентифицированные DSP, ограничение размера/deadline/RPS |
| `GET/POST events.adscale.example/openrtb2/notices/{kind}/{reference}` | Event Ingestion через отдельный event ingress | Проверка источника и непрозрачной ссылки; durable ACK; собственные тайм-ауты |
| `POST events.adscale.example/v1/events` | Event Ingestion | Показы/клики, контроль формата/размера/источника; браузерная auth отличается от mTLS DSP |
| `GET /livez`, `/readyz`, `/metrics` | Только приватные endpoints компонентов | Недоступны на публичном RTB host |
| Неизвестные host/path/method | Не маршрутизируется | 404/405; никаких wildcard proxy на внутреннюю сеть |

Домены в таблице — пример контракта. Публичные endpoint-адреса определяются перед подключением. Gateway не доверяет клиентским `X-Partner-Id`, `X-Forwarded-Client-Cert`, `X-AdScale-*`, `x-envoy-*`, deadline/retry/routing-заголовкам: удаляет их и формирует разрешённые значения сам. `traceparent` принимается только после проверки формата и не влияет на авторизацию или стоимость обработки.

Внутреннее соединение gateway → Bidding защищено mTLS и сетевыми правилами. Bidding обслуживает только identity gateway на публичном RTB listener; административные операции доступны по отдельной identity. Лимит привязан к credential/сертификату партнёра, а не к самостоятельно указанному ID.

## 3. Аутентификация

Основной вариант — mTLS с заранее согласованным CA/сертификатом DSP. Проверка выполняется на TLS handshake; постоянные соединения исключают handshake на каждый аукцион. SAN/identity сопоставляется локальной версионированной таблице `partner_id → policy`. IP allowlist используется как дополнительная мера, но не единственное подтверждение личности.

Если DSP не поддерживает mTLS, согласуется альтернативный локально проверяемый credential: короткоживущий подписанный JWT с `aud`, `iss`, `exp` и известным ключом. Public keys доставляются фоном; синхронной introspection/JWKS-загрузки на каждый bid нет. Неизвестный ключ или просроченное разрешение дают отказ, а не обход auth. Этот вариант включается только после согласования конкретного механизма с партнёром.

Ротация допускает ограниченное перекрытие старого и нового сертификатов/ключей; отозванная identity отключается конфигурацией и дренированием её соединений. Срок распространения revoke задаётся отдельно: существующий keep-alive не даёт бессрочного доступа. Локальные signing credentials загружаются из системы секретов, не включаются в конфигурационный репозиторий и не логируются. Для учебных локальных скриптов действует правило проекта: секреты только из `~/secrets.env`.

Браузерные пиксели не могут использовать mTLS площадки. Они валидируются по другому контракту Ingestion, защищаются от подделки и не получают права изменять баланс. Серверные billable-callback имеют собственную проверку подлинности; possession одной ссылки не заменяет согласованную проверку источника/подписи финансового факта.

## 4. Маршрутизация и балансировка

Global routing выбирает регион по близости и состоянию. Внутри него Envoy направляет новые запросы на ready-экземпляры Bidding с least-request балансировкой и ограничением in-flight. Прогрев модели предшествует readiness; liveness не используется как доказательство готовности ставок.

Canary выбирается по аутентифицированной DSP/стабильной когорте до отправки запроса. На первом включении новая DSP целиком обслуживается новым Bidding; legacy-партнёры мигрируют отдельно. Хеш бюджетного шарда вычисляет сам Bidding после чтения OpenRTB ID. Gateway не обязан разбирать всё JSON-тело ради выбора Redis-шарда.

Нельзя повторить один отправленный запрос на новом upstream, в другом регионе или на legacy при тайм-ауте. Следующие новые аукционы можно направлять по изменённой политике после оценки мощности. Повтор DSP использует тот же request ID и идёт в тот же регион владения в пределах окна дедупликации; при региональном отказе такой аукцион завершается no-bid/ошибкой, а не начинает новые обязательства в другом регионе.

Плавный deploy: drain соединений, прекращение приёма новых запросов, завершение in-flight в пределах их deadline; схемы событий и Redis keys совместимы с предыдущей версией. Перед массовым переключением gateway конфигурация проходит проверку, canary и автоматический rollback по техническим ошибкам/latency. Возврат на legacy ограничен его измеренной мощностью.

## 5. Ограничение нагрузки

Лимиты разделены на **контрактный RPS партнёра** и **ёмкость инфраструктуры**. Они не являются бюджетом рекламной кампании. Рабочая гипотеза для новой DSP — 3 000 RPS из прироста 15k →18k; подтверждается договором, а не выводится как обязательный контракт из арифметики.

### 5.1. Token bucket

Envoy применяет локальный token bucket по identity/route. При пустом bucket быстро возвращает 429; при договорённости с DSP возможен 204 с обязательным учётом технической причины. Для текущего аукциона это окончательный ответ, не приглашение повторять его после `Retry-After`.

Пример стартовой конфигурации для трёх равноправных gateway:

| Параметр | Значение / смысл |
|---|---|
| Лимит новой DSP по всему региональному пулу | 3 000 запросов/с |
| Доля одной из трёх реплик | 1 000 запросов/с |
| Локальный burst | 200 токенов; суммарно 600, то есть 200 мс дополнительного потока |
| Пополнение локального bucket | 10 токенов каждые 10 мс |
| Область bucket | На процесс Envoy, общий для worker threads; не на соединение |
| Ответ при переполнении | Немедленный 429 / согласованный технический no-bid |

Локальный лимит каждой реплики сам по себе не является глобальным: три реплики с лимитом 3k каждая дали бы до 9k. Поэтому control plane выдаёт доли регионального и партнёрского лимитов по эпохам; сумма активных долей ≤Q. При изменении количества реплик старая доля прекращает действовать до выдачи пересекающейся новой. Предлагаемая аренда доли — 5 с: потерявшая связь реплика не продолжает принимать трафик бесконечно. На холодном старте без доли — отказ; последняя подтверждённая конфигурация действует только до окончания аренды.

Новый сложный распределённый limiter не нужен для первого пилота: допустим фиксированный пул и статическое деление 3k на три узла. Цена — возможное недоиспользование при перекосе и временное снижение допуска после отказа узла. Для динамического перераспределения control plane и конечность lease должны быть реализованы явно; одного xDS push без механизма истечения недостаточно. Строгий глобальный счётчик на каждый запрос потребовал бы дополнительного RPC/хранилища и нарушил бы выбранную простоту критического пути.

Основание для области счётчика и token bucket: [Envoy Local rate limit](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/local_rate_limit_filter). Лимит соединений/IP, максимальные body/headers и защита TLS handshake дополняют RPS: аутентификация не защищает от ошибочного клиента с неограниченным числом соединений.

### 5.2. Concurrency и очереди

Для примера из трёх gateway стартовые ограничения upstream на процесс: `max_requests=400`, `max_pending_requests=0`, `max_connections=128`, retries отключены. Это кандидаты для теста, не рассчитанный production sizing. Суммарно до 1 200 in-flight относится ко всему пулу; значения не задаются как лимит каждой Bidding-реплики.

При измеренном среднем service time 40 мс закон Литтла даёт около `18 000 × 0,040 = 720` средних in-flight. P95/P99 вместо среднего в эту формулу не подставляются. Окончательные лимиты выбираются по хвостам, перекосу и отказу узла. `max_pending_requests=0` требует прогретых upstream connections; нехватка готового соединения вызывает быстрый отказ, а не накопление запросов.

Дополнительно само приложение имеет bounded worker pool и admission control: если остатка deadline недостаточно для текущей очереди, не начинать расчёт. Всплеск не разрешает неограниченное накопление work; масштабирование готовит новые реплики заранее, а не после исчерпания 80 мс.

## 6. Тайм-ауты и размыкатели

| Участок | Начальная политика |
|---|---|
| Приём заголовков/тела и auth на прогретом соединении | Цель ≤5 мс; размеры ограничены; медленный запрос обрывается по короткому request receive timeout |
| Соединение с upstream | `connect_timeout=5 ms`; keep-alive/HTTP2 pools; новые соединения прогреваются |
| Envoy route timeout | Максимум 55 мс после получения тела; уменьшается по общему оставшемуся бюджету |
| Полный запрос на ingress | Жёсткий верхний бюджет 65 мс от первого байта, включая получение тела, очередь, upstream и отправку ответа |
| Bidding | Применяет минимум общего остатка и ограничения `tmax`; Redis ≤6 мс внутри этого остатка |
| Upstream retries / hedging | Выключены, включая клиентские retry-заголовки |
| Event callback | Отдельный endpoint: предложенный HTTP budget 1 с, Kafka delivery budget 500 мс |

У Envoy разные таймеры измеряют разные участки. Route timeout не включает всё время получения запроса; одно `timeout: 65ms` не доказывает end-to-end 65 мс. Поэтому отдельно настраиваются receiving limits и общий stream timer, а gateway фиксирует origin времени запроса. Необходимый [набор таймеров Envoy](https://www.envoyproxy.io/docs/envoy/latest/faq/configuration/timeouts) проверяется на конкретной закреплённой версии.

Gateway передаёт доверенный абсолютный deadline/оставшийся бюджет в собственном заголовке, переписывая входное значение. Bidding переводит его в монотонный локальный таймер и дополнительно уменьшает по `tmax` из JSON. Между узлами требуется синхронизация часов; при использовании абсолютного времени задаётся предел skew (предлагается ≤1 мс) и запас на него. Нельзя передать `65 ms` заново каждому следующему hop. Пользовательский `grpc-timeout`/`x-envoy-upstream-rq-timeout-ms` не может продлить лимит.

Конкретный bounded deadline filter, если его нет в текущем ingress, является небольшим отдельным адаптером с контрактными тестами; стандартный Envoy не интерпретирует OpenRTB `tmax` автоматически. JSON `tmax` проверяет Bidding. Общий 65-мс timer gateway остаётся защитой даже при ошибке приложения.

Envoy circuit-breaking limits защищают пулы, а outlier detection исключает неисправные Bidding instances. Начальные параметры outlier: 5 последовательных transport/5xx ошибок, интервал оценки 1 с, base ejection 5 с, максимум 50% исключённых endpoints. Active readiness проверяется отдельно. Panic fallback на заведомо нездоровые endpoints выключается; при отсутствии healthy upstream — быстрый 503/договорной технический no-bid.

Не считать обычные 204 ошибками и не выбрасывать здоровую реплику за отсутствие подходящего объявления. Однако технический 204 внешне неотличим от бизнес-no-bid, поэтому Bidding передаёт внутрь gateway ограниченную категорию результата и экспортирует отдельные метрики. Внутренний заголовок с причиной удаляется перед ответом DSP. Метрики технических отказов запускают ограничение нагрузки/откат; их не заменяет только стандартный счётчик 5xx.

Открытие breaker зависимости Redis/Campaign/Finance и HALF_OPEN описаны в [interaction.md](interaction.md). Gateway не выполняет платный запрос для проверки восстановления: probes — health/status, без резервирования бюджета.

## 7. Мониторинг и SLO

Нужны три точки измерения: end-to-end у DSP, от первого байта до завершения ответа на gateway и server-side Bidding. Проверка только времени Auction Engine не подтверждает контракт. Гистограммы имеют плотные buckets возле 50/65/80/100 мс; P50/P95/P99 строятся по исходным buckets, а не усреднением перцентилей реплик.

| Сигнал | Разрез / действие |
|---|---|
| `rtb_request_duration_seconds` | DSP, region, route, release; отдельно все запросы и валидные аукционы |
| `rtb_outcomes_total` | bid, business-no-bid, technical-no-bid, auth failure, malformed, throttled, timeout |
| Stage latency | parse, candidates, auction, Redis, serialization; поиск источника хвоста |
| Envoy upstream latency / active / pending / overflow / ejections | Проверка пулов и распределения нагрузки |
| Projection age / grant availability / Redis generation | Закрытие небезопасных кампаний и оценка падения fill rate |
| Event lag / ACK failures / financial quarantine | Надёжность доставки и сверки |
| Доходность / fill rate / win rate | Сравнение canary с контролем; исключает «улучшение SLA» отказом всем |

`auction_id`, user ID и campaign ID не являются labels общих гистограмм: это неограниченная кардинальность. Они используются в ограниченных структурированных журналах и выборочных трассах с privacy-фильтрацией. Диагностические логи не блокируют ответ; их потери не смешиваются с финансовыми событиями.

Предлагаемый serving SLI: своевременные корректные bid и обоснованные business-no-bid / все валидные запросы в контрактном объёме. Technical-no-bid, отказ инфраструктуры, поздний ответ и отклонение в пределах обещанной ёмкости — неуспех. Запросы сверх договорной квоты выделяются отдельно и не исключаются из отчёта молча; формула знаменателя утверждается с DSP. Годовой ориентир availability — 99,9%; окно и условия штрафов определяются контрактом.

Предлагаемые сигналы тревоги: P99 ingress >65 мс в течение 5 минут; превышение agreed deadline у партнёра; technical failure >0,1% за 15 минут; короткий высокий всплеск ошибок; исчерпание error budget в коротком и длинном окнах. Порог 0,1% — рабочая цель, не уже измеренный результат. Отдельные немедленные alerts: неизвестная бюджетная generation, подтверждённая потеря события, конфликт финансового ключа. Сопровождение имеет назначенного владельца и инструкции, несмотря на отсутствие отдельного SRE.

## 8. Проверка перед подключением DSP

1. Contract tests: версия OpenRTB, content type, неизвестные поля, unsupported format, валюты, `tmax`, 200/204/400, auth, notification semantics.
2. Security tests: подмена partner/deadline/retry headers, чужой сертификат/ключ, просроченный credential, oversize и медленный body, попытка вызвать приватный endpoint.
3. Тест 18k совместно с событиями и тяжёлыми отчётами; исходные размеры payload и доля no-bid взяты из согласованного профиля, не только из «лёгких» запросов.
4. Отказ одного gateway/Bidding instance, skew нагрузки, исчерпание connections, смена количества реплик limiter; проверяется суммарная квота и восстановление.
5. Fault injection Redis/Kafka/Campaign/Finance: нет каскада retries, нет нового денежного резерва при неопределённом результате, есть своевременный технический отказ.
6. Совместный тест DSP, включая RTT/TLS/keep-alive и реальные точки замера. Без него нельзя объявить выполненными внешние 80 мс.

Проверка документов и рендеринг диаграмм не являются испытанием этой инфраструктуры. Реализация gateway filter, бюджетного протокола, outbox и consumer должна пройти указанные сценарии до production.
