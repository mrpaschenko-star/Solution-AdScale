# Спецификация Bidding Service

## 1. Назначение и границы

Bidding принимает запрос аукциона, выбирает допустимый креатив, рассчитывает цену и выдаёт обеспеченную бюджетом ставку до истечения deadline. Один экземпляр приложения объединяет обработку OpenRTB, таргетинг, расчёт аукциона и формирование ответа; вызовы между этими модулями локальные. Основу составляет существующий C++ Auction Engine. Для проекта выбран C++ serving-процесс с HTTP-адаптером и отдельными пулами фоновых задач; переход на другой язык не является частью выделения.

| Внутри Bidding | За границей Bidding |
|---|---|
| Адаптеры площадок, валидация профиля OpenRTB | Создание/редактирование кампании — Campaign |
| Подбор, таргетинг, правила аукциона, pacing | Авторитетный баланс, платежи, ledger — Finance |
| Локальная read-модель и её версии | Доставка файлов и HTML/JS после аукциона — Delivery/CDN |
| Использование выделенных квот и резервы ставок | Приём фактических показов/кликов/уведомлений — Event Ingestion |
| Идемпотентный результат запроса, deadline и no-bid | Агрегаты и отчёты — Analytics |

Код Bidding не получает credentials к Campaign/Finance PostgreSQL. В первые три месяца владельцы Campaign и Finance могут оставаться модулями монолита, но предоставляют те же контракты. Микросервисная граница не требует немедленного переноса всей OLTP-БД.

Компоненты: [component-bidding.puml](diagrams/component-bidding.puml). Сам Bidding состоит из ingress adapter, orchestrator, candidate index, auction core, quota client, response builder и projection manager. Projection manager выполняет фоновые операции; его очереди, соединения и CPU ограничены отдельно от RTB.

## 2. Зависимости

| Зависимость | Для чего нужна | Когда вызывается | При отказе |
|---|---|---|---|
| Локальная immutable read-модель | Статусы, таргетинг, ставки, креативы | Каждый запрос, из памяти | Нет готовой/свежей модели — no-bid для затронутого шарда |
| Redis Bidding | Атомарный резерв и идемпотентный результат | Один вызов на финализацию решения | No-bid; запрещён fallback в PostgreSQL |
| Campaign Snapshot gRPC | Метаданные согласованного снимка и позиции журнала | Прогрев / восстановление | Повтор вне RTB; новая реплика не ready |
| Object storage | Получение проверенного снимка | Прогрев / восстановление | Старый безопасный снимок только при живом потоке актуализации |
| Kafka | Изменения кампаний, квот и результатов расчёта | Фоновое потребление | Контроль watermark/аренды, затем закрытие затронутых кампаний |
| Finance Quota gRPC | Выделение/сверка квот | Фоновые запросы | Только уже выданный подтверждённый лимит |
| Telemetry collector | Метрики и выборочные трассы | Асинхронно, ограниченный буфер | Допускается потеря диагностических трасс; не финансовых событий |

Delivery не вызывается для сборки каждого bid-response: проверенные шаблоны `adm`/ссылки на креатив включены в read-модель. Никаких запросов внешнего профиля пользователя или загрузки модели ML на пути ставки. Если позже понадобится такая зависимость, она должна получить отдельный бюджет и безопасный fallback.

## 3. API ставок: OpenRTB поверх HTTPS

### 3.1. Входной контракт

Внешний endpoint: `POST /openrtb2/auction`. Площадка определяется по аутентифицированной identity, а не по полю тела. Внутри gateway запрос идёт на тот же HTTP endpoint Bidding. OpenRTB — стандартизованный аукционный JSON API, а не CRUD REST.

Предлагаемый профиль интеграции — OpenRTB 2.6, HTTPS с keep-alive. Заголовки: `Content-Type: application/json`, `x-openrtb-version: 2.6`. `id` идентифицирует запрос, `imp[].id` — рекламную возможность; `tmax` включает сетевое время. Цена ответа задаётся в CPM. Успешная ставка возвращается с HTTP 200, обычный no-bid — HTTP 204 без тела, некорректный OpenRTB — HTTP 400 без тела. Неизвестные дополнительные поля не должны ломать совместимость. Основание: [официальная спецификация OpenRTB 2.6](https://github.com/InteractiveAdvertisingBureau/openrtb2.x/blob/main/2.6.md).

В пилоте поддерживаются баннеры, одна валюта по договору и одна `imp` на запрос. Максимум одна ставка на неё. Video/native, deal-specific аукционы и несколько `imp` подключаются отдельными контрактными тестами. Это ограничение требует согласия DSP: валидный неподдерживаемый формат даёт no-bid, а не ошибку JSON. Если пилотный профиль не покрывает обязательный трафик площадки, объём реализации увеличивается до запуска.

| Поле / условие | Проверка и поведение |
|---|---|
| `id`, `imp[].id` | Непустые строки, согласованный предел 128 байт; идентичность в пространстве партнёра |
| `imp[].banner`, размеры и secure | Поддерживаемый формат и подходящий безопасный креатив |
| `site` / `app`, пользовательские сигналы | Достаточность для выбранных правил; при отсутствии consent не использовать персонализированные признаки |
| `cur`, floor и цена | Только согласованная валюта; не угадывать курс; поддерживаемая модель floor |
| `at` и ограничения площадки | Только поддерживаемые правила, блок-листы и seats; неизвестная существенная семантика — no-bid |
| `tmax` | Положительное целое; уменьшает локальный бюджет, не увеличивает договорные 80 мс |
| `X-Auction-Created-At` (предлагаемое расширение) | Подтверждённое источником неизменяемое время создания; защита от позднего replay. Порог возраста и clock skew согласуется с DSP; не заменяет `tmax` |
| `test` | Тестовый трафик направляется в отдельную квоту без реальных списаний |
| Payload | Предлагаемый максимум 64 KiB после распаковки; глубина JSON ≤32; reject oversized до дорогостоящей обработки |

Иллюстративный запрос; идентификаторы, домены и деньги вымышлены:

```json
{
  "id": "auction-9001",
  "at": 1,
  "tmax": 80,
  "cur": ["USD"],
  "imp": [{
    "id": "imp-1",
    "banner": {"w": 300, "h": 250},
    "bidfloor": 0.5,
    "bidfloorcur": "USD",
    "secure": 1
  }],
  "site": {"id": "site-7", "domain": "publisher.example"},
  "device": {"devicetype": 2},
  "test": 1
}
```

### 3.2. Результат и ошибки

```json
{
  "id": "auction-9001",
  "bidid": "response-9001",
  "cur": "USD",
  "seatbid": [{
    "seat": "adscale",
    "bid": [{
      "id": "bid-9001",
      "impid": "imp-1",
      "price": 1.25,
      "crid": "creative-17-v3",
      "adomain": ["advertiser.example"],
      "w": 300,
      "h": 250,
      "adm": "<a href=\"https://ads.example/click/r-demo\"><img src=\"https://cdn.example/c17-v3.png\" width=\"300\" height=\"250\"></a>",
      "nurl": "https://events.example/openrtb2/notices/win/r-demo",
      "burl": "https://events.example/openrtb2/notices/billable/r-demo?price=${AUCTION_PRICE}"
    }]
  }]
}
```

Пример показывает форму сообщения, но не production-токен и не полноценный контракт трекинга. В production `r-demo` заменяется непрозрачной ссылкой на резерв с проверкой подлинности и сроком действия; URL не содержит API-ключей, пользовательских идентификаторов или баланса. Если путь содержит токен-корреляцию, он удаляется из access-логов. Цена из callback принимается только после проверки источника и формата, не из произвольного браузерного запроса. Креативы заранее проверяются и версионируются.

Ссылка несёт проверяемое `reservationProof`: bid/request/imp ID, grant/generation, campaign version, currency, верхнюю стоимость и срок допустимого расчёта. Оно подписывается Bidding; при необходимости скрыть внутренние ID — также шифруется для Ingestion/Finance. Это ограниченное доказательство одного резерва, а не credential доступа к API. Доказательство и готовый ответ сохраняются атомарно с резервом и выходят за пределы Bidding только после успешного ACK. Finance проверяет proof локально и сверяет grant в собственной БД, не читает Redis другого сервиса. Если отдельная запись резерва ещё не поступила, проверенный proof позволяет создать её при первом авторитетном уведомлении в пределах уже заблокированного grant. Непроверяемый proof — карантин, а не автоматическое списание.

`nurl` означает выигрыш, но не гарантирует billable-показ. `burl` вызывается по согласованному правилу тарификации. Нельзя списывать деньги за само формирование ответа или одновременно за `nurl`, пиксель и `burl`. См. [разделы уведомлений OpenRTB](https://github.com/InteractiveAdvertisingBureau/openrtb2.x/blob/main/2.6.md).

| Ситуация | Внешний ответ | Внутренний результат / учёт |
|---|---|---|
| Есть безопасная ставка | 200 + BidResponse | `BID` |
| Нет кандидата / бюджета / поддерживаемого формата | 204, пустое тело | `NO_BID_BUSINESS` + причина |
| Deadline, stale state, открытый breaker зависимости | 204, если согласовано с DSP | `NO_BID_TECHNICAL`; техническая деградация в SLI |
| Повреждённый запрос или повтор ID с другим содержимым | 400, пустое тело | Ошибка контракта, без раскрытия стека |
| Ошибка аутентификации / полномочий | 401/403 либо отказ TLS | Считает gateway, запрос не попадает в Bidding |
| Rate limit | 429; допускается договорной mapping в 204 | Причина overload остаётся в метриках |
| Необработанная ошибка / нет доступных upstream | 503, если не согласован технический no-bid | Ошибка; нельзя выдавать за обычное отсутствие кандидата |

Готовые HTTP 400/401/403 не превращаются в 204. Отображение технических ошибок в no-bid — часть партнёрского контракта, а не способ скрыть SLA. Для RTB не применяется общий REST-формат `problem+json`; служебные REST API, напротив, могут использовать его.

### 3.3. Deadline

Gateway начинает таймер при первом байте запроса. Рабочая верхняя граница:

`D_local = min(65 ms, tmax_effective - 15 ms)`, где `tmax_effective = min(tmax, 80 ms)`, а при отсутствии `tmax` берутся договорные 80 мс.

15 мс — предлагаемый общий запас для внешней сети, проверяемый совместно с DSP. Без доверенной точки отправки нельзя измерить фактическую уже потраченную входящую задержку; гарантия 80 мс требует тестов на канале партнёра. Отрицательный/слишком малый остаток означает немедленный no-bid. Таймер не перезапускается после маршрутизации, чтения тела или перехода между этапами.

Для обычного 80-мс запроса: ingress/проверки 5 мс, кандидаты 12, аукцион 20, Redis 6, ответ 7, внутренний запас 15. Это бюджет этапов, а не сумма измеренных перцентилей. Cancellation проверяется между этапами и перед резервом. Успешный резерв после потери клиента не освобождается автоматически: ответ мог попасть партнёру.

## 4. Служебные API

На отдельном приватном listener с mTLS: `GET /livez` — жив процесс; `GET /readyz` — загружены модель и версии, разрешён serving; `GET /metrics` — Prometheus. Эти endpoints не публикуются на DSP virtual host. Недоступность данных одной кампании закрывает её, а не обязательно весь процесс. Потеря способности резервировать весь обслуживаемый шард делает экземпляр not ready.

Отдельный unary gRPC API реализуется владельцами Campaign и Finance и вызывается фоном из Bidding:

| Метод | Запрос | Ответ / семантика |
|---|---|---|
| `adscale.campaign.v1.SnapshotService/GetManifest` | `region`, `projection_schema_version`, `known_snapshot_id` | `snapshot_id`, ссылка на immutable объект, SHA-256, размер, версии правил, topic/partition/offset checkpoint |
| `adscale.finance.v1.QuotaService/AllocateGrant` | `allocation_request_id`, `campaign_id`, `currency`, `region`, `shard_id`, `generation`, `amount_micros` | Неизменяемый `grant_id`, сумма, epoch, срок разрешения. Повтор ключа не создаёт новый резерв |
| `adscale.finance.v1.QuotaService/GetGrantStatus` | `grant_id` | Выделенная сумма, состояние, epoch, разрешённость использования; не остаток Redis |

Запросы/ответы типизированы Protobuf; package `v1` меняется только при несовместимом контракте. Денежные значения — `int64` в micros и строка ISO-валюты. Удалённые field numbers резервируются; новые поля optional, неизвестные enum обрабатываются безопасно. Snapshot schema имеет собственную версию и не подменяет версию API.

Начальные deadlines: manifest/status 300 мс, allocate 500 мс. `INVALID_ARGUMENT`/`PERMISSION_DENIED` не повторяются; `UNAVAILABLE`/`DEADLINE_EXCEEDED` повторяются по политике из interaction.md. Нулевой баланс — бизнес-результат `INSUFFICIENT_FUNDS`, а не повод открыть breaker. На первом этапе эти контракты реализуют адаптеры соответствующих модулей монолита.

## 5. Модель данных и владение

### 5.1. Локальные read-модели

| Сущность | Ключевые поля | Хранение и правила |
|---|---|---|
| `CampaignProjection` | `campaign_id`, `advertiser_id`, `version`, `status`, targeting, `currency`, `base_bid_cpm_micros`, `max_bid_cpm_micros`, creative refs, effective dates | Immutable индекс в памяти; только производная копия Campaign |
| `CreativeProjection` | `creative_id`, `version`, формат/размер, `adomain`, проверенный шаблон/URL, approval state | В памяти; версия фиксируется в решении |
| `ProjectionCheckpoint` | `snapshot_id`, schema, offsets по разделам, applied watermark, validity lease | Память и снимок; готовность после полного replay до согласованной отметки |
| `PartnerPolicy` | partner identity, разрешённые форматы, валюта, deadline, тарификация, версии адаптера | Версионированная конфигурация с локальной копией; изменение проходит canary |

Каждый serving-экземпляр, которому нужна полная read-модель, получает все необходимые изменения. Он имеет собственную consumer group/собственный replay, а не делит одну общую group с другими копиями полного индекса: иначе обновления разделятся между репликами. При дальнейшем шардировании каждая реплика шарда получает весь поток этого шарда. Цена fan-out оценивается по частоте изменений кампаний, а не по числу bid requests.

Снимок создаётся на согласованном барьере между исходными версиями и журналом. Manifest содержит точные offsets продолжения; схема «снять таблицы, потом подписаться с latest» недопустима. При неполном replay реплика не ready. Обновление собирается в новой immutable версии и атомарно подменяет указатель; запрос видит согласованную версию.

Обычные изменения: предлагаемый P99 ≤5 с. Heartbeat/watermark подтверждает, что предшествующие изменения обработаны. При отсутствии подтверждения >10 с шард/кампания закрывается. Возраст последнего изменения самой кампании не является возрастом проекции. Срочная остановка использует приоритетное изменение и короткое разрешение на участие; мгновенная глобальная остановка этим решением не обещается.

### 5.2. Квоты, резервы и идемпотентность

| Сущность | Поля | Источник истины |
|---|---|---|
| `BudgetGrant` | `grant_id`, `allocation_request_id`, campaign, currency, region, shard, generation, `allocated_micros`, state, lease | Finance PostgreSQL: сумма целиком заблокирована до подтверждённого возврата |
| `GrantRuntime` | `grant_id`, generation, `available_micros`, `held_micros`, settlement version | Redis Bidding: используется только внутри выделенной суммы |
| `BidReservation` | `reservation_id`, request key, `bid_id`, `imp_id`, grant, campaign version, `max_charge_micros`, state | Redis для текущего serving; подтверждённые расчёты — Finance; при утрате состояния вся сомнительная квота замораживается |
| `RequestDecision` | `(partner_id, request_id)`, canonical fingerprint, response/причина, first deadline, reservation ref | Redis, атомарно с резервом; ответ повторно выдаётся только пока он ещё допустим |
| `SettlementInbox` / `LedgerEntry` | business key, payload hash, amount, currency, reservation, timestamps | Finance PostgreSQL, уникальные ограничения и единая транзакция |

Суммы хранятся целыми micros (`1 единица валюты = 1 000 000 micros`). Цена CPM не равна стоимости одного показа: для ставки 1,25 USD CPM верхняя цена показа — 0,00125 USD = 1 250 micros до согласованных комиссий. Округление верхнего резерва — вверх; комиссии входят в резерв. Floats не используются для финансовой арифметики. В пилоте выбран first-price CPM; другой `at` не включается без тестов и явной верхней границы обязательства.

Инварианты:

- Finance блокирует средства транзакционно: уже проведённый расход + остаток средств, закреплённых за grants (без уже проведённого расхода), + свободный остаток равны обеспеченным средствам с учётом разрешённых корректировок. Проведённая часть grant не учитывается повторно как активная блокировка. Повтор grant не создаёт новые деньги.
- Внутри каждого grant: `available + held + spent = allocated`; значения неотрицательны. Списание переводит часть `held` в `spent`, подтверждённое освобождение возвращает остаток в `available`.
- На один уникальный billable-факт — одна проводка; дубли транспортных сообщений не меняют баланс.
- Потеря ответа, истечение Redis TTL или HTTP deadline сами по себе не дают права вернуть удержанные деньги.

### 5.3. Один атомарный вызов на решение

Запрос стабильно попадает в serving-шард по `(partner_id, request_id)`. На каждом шарде заранее есть небольшие квоты нужных кампаний; суммарно они обеспечены Finance. В Redis Cluster ключи решения, выбранного grant и резерва имеют общий hash tag шарда, например `{s17}`. Нельзя обещать атомарный Lua-скрипт над случайными ключами разных slots.

После чистого расчёта кандидата Bidding вызывает `FinalizeDecision` (Redis function/Lua):

1. Проверить ключ запроса. При том же fingerprint вернуть существующий допустимый результат без повторного резерва; при другом — конфликт контракта.
2. Проверить generation, разрешение и остаток grant; для ставки проверить верхнюю стоимость. Отсутствие ключа grant не означает «восстановить полный лимит».
3. Атомарно уменьшить доступную сумму, создать резерв и сохранить готовый ответ с его допустимым сроком. Для обычного no-bid сохранить результат без денежного резерва.
4. Вернуть окончательное решение. Только после подтверждения этой операции можно отправлять ставку DSP.

Ответ, токен корреляции и `bid_id` подготавливаются до вызова; финансовых эффектов до финализации нет. Повтор может снова выполнить чистый расчёт, но скрипт выбирает уже сохранённое решение. Если сохранённый ответ просрочен, возвращается no-bid без нового резерва. При timeout Redis результат неизвестен: для этого HTTP-запроса выдаётся технический no-bid, а сомнительный резерв удерживается. Нельзя повторить резерв с новым `reservation_id`.

В пилоте дедупликационные tombstones хранятся минимум 10 минут; кэш полного ответа — только до его допустимого deadline. Это требует соглашения с DSP об уникальности request ID и максимальном окне повторов. Чтобы отвергать поздний replay после удаления tombstone, профиль предусматривает аутентифицированное неизменяемое время создания аукциона в согласованном заголовке `X-Auction-Created-At` и проверку допустимого возраста/clock skew. Это расширение интеграционного контракта, не стандартное обязательное поле OpenRTB. Если партнёр его не поддерживает, срок хранения ключей должен покрывать весь договорной replay horizon; распознать произвольно поздний повтор по одному ID после удаления состояния невозможно. Финансовые резервы и дедупликация расчётов живут по более длинному договорному окну окончательности, а не по RTB TTL.

Стоимость состояния учитывается отдельно: 18 000 решений/с × 600 с = 10,8 млн tombstones. Даже при условных 100 байтах это 1,08 GB без overhead и репликации; реальную память определяет бенчмарк. Квоты по шардам фрагментируют бюджет, поэтому гранты выдаются по спросу, а число шардов меняется только с дренированием дедупликационного окна и согласованным переносом владения.

### 5.4. Failover Redis и окончательность денег

Redis не объявляется надёжным ledger. Репликация/AOF уменьшают риск потерь, но не дают права продолжать со старым остатком после неопределённого переключения. Runtime generation привязана к конкретному активному поколению primary; прозрачное переключение с автоматическим продолжением расходования запрещено. Смена роли/идентификатора primary или неопределённый разрыв переводят затронутые grants в `FROZEN`.

Координатор восстановления ограждает старый primary, ждёт окончания старых разрешений и подтверждает это до выдачи новых. Финансовый владелец сохраняет всю сомнительную старую сумму заблокированной; восстановленный снимок Redis не уменьшает её автоматически. Новая generation получает только новую независимо обеспеченную квоту. Если fencing или происхождение состояния не подтверждены, соответствующий шард остаётся закрытым. Этот протокол обязателен для production; обычный Redis auto-failover без такой интеграции финансовые инварианты не обеспечивает.

Состояния резерва: `HELD` → `SETTLED` либо `RELEASED`; из неопределённого состояния — `FROZEN` до сверки. Win лишь уточняет состояние аукциона. Освобождение допустимо по авторитетному loss/финальному расчёту и правилам контракта. Если возможны поздние billable-события, до конца согласованного окна окончательности деньги удерживаются. Позднее событие после финализации попадает на сверку; тихий повторный debit запрещён.

## 6. Выделение из монолита

1. Вынести старый алгоритм за стабильный интерфейс и воспроизвести его на контрольном наборе; текущие правила остаются эталоном до согласованных изменений.
2. Ввести outbox в Campaign/Finance, построить snapshot + replay, дать Bidding доступ только к API и событиям.
3. Запустить shadow без реальных резервов, callback и ставок; сравнивать кандидатов, цену и причины отказа. Теневой трафик ограничивается по CPU.
4. Перевести небольшую стабильную когорту на Bidding, отделив её бюджет от legacy. Один request имеет одного реального владельца; gateway не зеркалирует финансовые side effects.
5. После приёмки расширять долю. Откат — на прошлую стабильную версию или ограниченный legacy-путь; legacy на 15k не принимает автоматически все 18k. Контракты схем сохраняются на период отката.

Горизонтально масштабируются реплики Bidding с предварительным прогревом. Квоты и дедупликация разделяются по стабильным шардам; увеличение числа процессов не умножает доступный бюджет. Для регионального отказа действуют ограничения задания 1: новый регион не расходует сомнительный остаток потерянного, а повтор уже начатого аукциона не запускается там автоматически.
