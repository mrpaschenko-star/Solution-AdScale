## Основные решения

1. **Bidding — единый сервис критичного пути.** RTB-адаптер, подбор, аукцион и ответ выполняются в одном процессе. Campaign, Finance, Delivery и аналитика не вызываются на каждый bid request.
2. **Envoy — региональный DSP gateway.** Это развитие RTB ingress из задания 1. Он передаёт OpenRTB JSON в Bidding без преобразования в gRPC и без второго management gateway.
3. **Campaign: gRPC для служебных запросов, Kafka для изменений.** Готовые данные читаются из памяти Bidding. REST остаётся API управления кампаниями для кабинета.
4. **Региональный Redis — обязательная зависимость резервирования.** Перед выдачей ставки один атомарный вызов фиксирует резерв и результат идемпотентной обработки. Квота заранее обеспечена блокировкой денег в Finance.
5. **События идут через Kafka.** Приём подтверждается после устойчивой записи; Finance защищает проводки транзакционной идемпотентностью, Analytics строит собственную проекцию.
6. **Быстрый отказ безопаснее необеспеченной ставки.** Устаревшая кампания, недоступный резерв или истёкший deadline приводят к no-bid. Кеш и дефолтная ставка допустимы только при соблюдении тех же ограничений.

## Границы уверенности

Задание называет отправителя bid requests «DSP». Это название сохранено; в стандартной модели OpenRTB запрос обычно идёт от exchange/SSP к bidder. Перед интеграцией нужно подтвердить реальную роль партнёра и согласовать профиль OpenRTB.

Ниже выбраны рабочие значения тайм-аутов, burst, freshness и retry-политик. Если значение не дано в кейсе, оно является **проектным предложением**, а не подтверждённым свойством системы. В частности, до запуска нужно согласовать:

- точку измерения и семантику 80 мс, `tmax`, поддерживаемую редакцию OpenRTB 2.6;
- формат баннеров, валюты, аукционную модель, происхождение и окончательность billable-события;
- идентификаторы/повторы уведомлений, сроки поздних событий и сверки; тайм-аут не означает проигрыш;
- лимит новой DSP: 3 000 RPS соответствует только разнице между 18 000 и 15 000, а не согласованному контрактному пику;
- допустимость остановки кампании с задержкой до 10 с и временной блокировки сомнительных квот.

## Приёмка

| Проверка | Критерий |
|---|---|
| Совместный профиль 18k RPS, события, управление и отчётность | Новый DSP соблюдает согласованный SLA; текущие клиенты P95 ≤100 мс; нет зависимости RTB от OLTP/Analytics |
| Отказ Campaign / Finance | Свежая подтверждённая проекция и уже выделенные средства используются только в пределах разрешений; затем своевременный no-bid |
| Redis timeout / failover | Нет повторного резерва с новым ключом; затронутые квоты заморожены; нет перерасхода |
| Дубли billable-событий и падение consumer после commit | Одна проводка на бизнес-событие, повтор безопасен |
| Отказ брокера / зона | Нет ложного ACK до устойчивой записи; видны lag, retries и технические потери до приёма |
| Rate limit, breaker, deadline | Быстрый контролируемый отказ, отсутствие retry storm и возвращения просроченных ставок |
| Shadow и canary | Shadow без денежных эффектов; real request обслуживается одним путём; откат учитывает мощность legacy |

Контрольный прогон: 60 минут целевой нагрузки и 15 минут всплеска +30% с последующим восстановлением. Всплеск проверяет управляемую деградацию, а не обещает полный SLA выше рассчитанной мощности. Результат оценивается по latency, ошибкам, техническим no-bid и доходности контрольной группы: выдача одного no-bid всем запросам не считается выполнением цели.
