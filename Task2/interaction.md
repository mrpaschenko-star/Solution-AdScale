# Взаимодействия и паттерны надёжности

## 1. Выбор протоколов

| Связь | Выбор | Почему | Отклонённая альтернатива |
|---|---|---|---|
| DSP → Envoy → Bidding | OpenRTB 2.6 JSON / HTTPS с keep-alive | Совместимость с площадкой; Bidding отвечает в той же сессии; gateway не перекодирует тело | Внешний gRPC потребовал бы изменения DSP; Kafka не подходит для ответа аукциона за десятки миллисекунд |
| Модули внутри Bidding | In-process C++ interfaces | Нет сетевых переходов между подбором и Auction Engine | Отдельный REST/gRPC hop на каждую стадию добавляет задержки и частичные отказы |
| Bidding → Campaign | Unary gRPC для manifest при прогреве; Kafka для дальнейших изменений | Типизированный межсервисный контракт, deadlines, generated clients; массовые данные загружаются из object storage | REST технически подходит, но для машинного snapshot-контракта выбран gRPC; синхронный запрос кампании на каждый bid исключён при любом протоколе |
| Кабинет → Campaign | REST/JSON через management API | Простое CRUD, удобство Web UI, `ETag`/`If-Match` для конкурентных изменений | gRPC-Web потребует адаптера без необходимого здесь выигрыша |
| Bidding → Finance | gRPC AllocateGrant / GetGrantStatus, только фоном | Идемпотентные операции и строгие типы денег/epoch | Синхронный debit на каждую ставку связывает availability и latency с ledger |
| Bidding → Redis | Redis protocol, атомарная function/Lua | Резерв и решение в одной атомарной операции в одном slot | GET+SET снаружи создаёт гонку; SQL на primary возвращает исходную связанность |
| Campaign/Finance → потребители | Kafka из transactional outbox | Нет потери между commit исходной транзакции и публикацией; версии и replay | Две независимые записи «БД, затем Kafka» оставляют окно потери |
| Сайт/приложение/DSP → Event Ingestion | HTTPS, отдельный endpoint | Снаружи нельзя выдавать доступ к брокеру; валидация и защита до публикации | Прямой Kafka producer в браузере неуправляем и небезопасен |
| Event Ingestion → Finance/Analytics | Kafka, отдельные consumer groups | Буферизация, пакетирование, независимый темп обработки, восстановление | REST fan-out связывает отправителя с медленнейшим потребителем; Redis Pub/Sub не хранит события |

Выбор gRPC не является обещанием «быстрее REST» без измерений. Главный выигрыш — устранение удалённого чтения кампаний из критического пути. На первом этапе gRPC реализуется адаптером модуля Campaign внутри монолита; готовый REST endpoint можно временно оставить за тем же интерфейсом Bidding, если это уменьшает срок интеграции и проходит контрактные проверки. Целевой контракт остаётся описанным в [спецификации сервиса](bidding-service.md).

## 2. Взаимодействие по времени

### 2.1. Ставка

[Sequence: RTB](diagrams/sequence-bid.puml). Gateway проверяет identity, лимит и доступность Bidding. Сам Bidding проверяет актуальность модели, рассчитывает ставку, атомарно резервирует сумму и сохраняет ответ в Redis. Лишь после подтверждения резерва возвращается bid. Campaign, Finance, Kafka и Delivery не вызываются синхронно в этом запросе.

Запрос не ставится в неограниченную очередь. Нагрузка, которую нельзя выполнить до deadline, отклоняется заранее. На этом пути **нет автоматических retries, hedged requests или failover того же запроса на legacy**. Потеря соединения не доказывает, что upstream не успел зарезервировать средства или отправить ответ.

### 2.2. Обновление кампаний и прогрев

[Sequence: campaign](diagrams/sequence-campaign.puml). Campaign записывает изменение и outbox в одной транзакции. Publisher может отправить событие повторно; потребитель проверяет `event_id` и версию агрегата. Для первого запуска Bidding получает manifest, загружает snapshot, проверяет SHA-256 и schema, дочитывает Kafka от checkpoint и только после этого становится ready.

Kafka offsets в manifest относятся к точке согласованности снимка. При out-of-order событии старая версия игнорируется; разрыв версии требует дочитать журнал или перестроить проекцию, а не просто перепрыгнуть на последнюю. Heartbeat не должен обходить предыдущие записи соответствующего раздела. При разрыве до истечения freshness можно продолжать только по последней подтверждённой допустимой версии, после границы — no-bid.

### 2.3. Событие и финансовая обработка

[Sequence: settlement](diagrams/sequence-events.puml). Тело callback проверяется до публикации, ACK выдаётся после устойчивой записи в Kafka. Finance транзакционно дедуплицирует бизнес-факт, проводит расчёт и создаёт outbox результата; offset подтверждается после commit. Если процесс упадёт между commit и offset, replay увидит уже обработанный факт.

Изменение read-модели бюджета Bidding идёт по `SettlementApplied` с `settlement_id` и версией, поэтому повтор не освобождает резерв второй раз. Analytics обрабатывает тот же исходный поток в отдельной group. Финансовый итог в интерфейсе берётся из Finance; запаздывающая аналитика не определяет доступные деньги.

## 3. Kafka: данные и доставка

### 3.1. Потоки

| Topic, версия 1 | Ключ раздела | Producer → consumers | Правило |
|---|---|---|---|
| `campaign.changes.v1` | `campaign_id` | Campaign outbox → проекции Bidding/Delivery/Analytics | Порядок по кампании, монотонная aggregate version |
| `budget.grants.v1` | `grant_id` | Finance outbox → Bidding | Неизменяемый grant; повтор не переинициализирует израсходованный остаток |
| `ad.impressions.v1` | `auction_id` | Ingestion → Analytics / архив | Проверка происхождения, транспортные дубли допустимы |
| `ad.clicks.v1` | `auction_id` | Ingestion → Analytics / антифрод / архив | Клик не означает автоматический debit в выбранном CPM-профиле |
| `auction.notices.v1` | `reservation_id` | Ingestion → Finance / Analytics | Win, loss, billable; порядок между типами не предполагается |
| `finance.settlements.v1` | `grant_id` | Finance outbox → Bidding / Analytics | Подтверждённый результат, идемпотентное изменение резерва |

В данном CPM-пилоте только подтверждённое `billable` приводит к списанию. Если договор считает показ из другого источника, меняется правило нормализации, а не добавляется второй независимый debit. Разные topics не имеют общего порядка. Допускается billable до win, задержка loss и повтор каждого сообщения.

Пример нормализованного события, сформированного после проверки callback:

```json
{
  "eventId": "event-6001",
  "eventType": "AuctionBillable",
  "schemaVersion": 1,
  "source": "partner-new-dsp",
  "occurredAt": "2026-10-24T10:00:00.000Z",
  "receivedAt": "2026-10-24T10:00:00.050Z",
  "partnerId": "new-dsp",
  "partnerEventId": "settlement-801",
  "auctionId": "auction-9001",
  "impId": "imp-1",
  "bidId": "bid-9001",
  "reservationId": "reservation-9001",
  "reservationProof": "opaque-demo-proof",
  "grantId": "grant-37",
  "region": "region-a",
  "campaignId": "campaign-42",
  "campaignVersion": 17,
  "currency": "USD",
  "amountMicros": 1250,
  "priceBasis": "IMPRESSION",
  "traceId": "trace-example"
}
```

`amountMicros` — уже проверенная цена одного события, а не сырое CPM-значение callback. Все ID и proof примера вымышлены. Проверяемый `reservationProof` переносит ограниченное доказательство резерва из Bidding; Finance сверяет его с собственным grant без прямого чтения Redis Bidding. Schema фиксирует обязательные поля, типы и значение `priceBasis`; несовместимые изменения требуют нового event type/schema и адаптации потребителей. Новые optional-поля добавляются совместимо. Сохраняются время события и время приёма; локальные часы не используются для доказательства порядка между системами.

### 3.2. Надёжность журнала

- Kafka в одном регионе, replication factor 3 по трём зонам, `min.insync.replicas=2`, `acks=all`, unclean leader election выключен. При отсутствии достаточного ISR запись не подтверждается. Реальная топология должна поддерживать такую схему.
- Producer idempotence включён; он сокращает дубли в пределах producer session, но не заменяет бизнес-дедупликацию после рестарта, outbox replay или повторного HTTP callback.
- Outbox помечается опубликованным только после ACK Kafka. Ошибка после публикации до пометки даёт повтор с тем же event ID. Очистка outbox выполняется по retention с учётом незавершённых публикаций.
- Финансовый consumer коммитит offset после транзакции. Для пакетной обработки коммитится только непрерывно обработанный диапазон offset, чтобы не перескочить через ошибку.
- Массовые topics и финансовые уведомления имеют отдельные client quotas и consumer pools. Брокерный диск, ISR, lag и темп заполнения контролируются; «есть Kafka» не означает бесконечный буфер.
- Число partitions и retention рассчитываются по events/s, байтам, перекосу ключей и времени восстановления. Начальные рабочие предложения: 24 часа для сырых clicks/impressions и 7 суток для управляющих/финансовых topics, при условии проверки стоимости и требований к данным. Долгий replay — из object storage. Retention брокера не равен юридическому сроку финансового аудита.
- `campaign.changes` можно дополнить compacted read-моделью, но compaction не заменяет необходимую историю replay; tombstones и снимки обрабатываются явно.

При отказе брокера Ingestion возвращает временную ошибку для серверного callback, а партнёр повторяет по согласованной политике. Нельзя отправить 204, если событие находится только в RAM. Потери до durable ACK не покрываются гарантией Kafka. Для браузерного пикселя надёжный retry не гарантируется: это отдельно измеряемая потеря; такие события не должны быть единственным финансовым доказательством без договорного механизма сверки.

Финансовое сообщение с неизвестным резервом, несоответствующей валютой или суммой выше верхнего резерва помещается в устойчивый карантин и вызывает alert. Оно не списывается автоматически. Если обработка следующего события зависит от него, соответствующая последовательность/partition приостанавливается. DLQ/карантин — очередь расследования с владельцем и replay, а не место удаления неудобных событий.

## 4. Circuit Breaker и изоляция ресурсов

| Место | Механизм | Предлагаемая стартовая политика | Поведение |
|---|---|---|---|
| Envoy → Bidding | Ограничения connections/in-flight/pending + outlier detection | Числа из api-gateway.md | Не отправлять в переполненный пул/неисправный экземпляр |
| Bidding → Redis | Классический breaker на шард/primary generation | 5 последовательных транспортных ошибок либо ≥50% ошибок за 10 с при ≥100 вызовах | Открыть на 1 с + jitter; no-bid, без обращения к OLTP |
| Projection manager → Campaign | Breaker на endpoint служебного API | 5 последовательных сбоев либо тот же error-rate порог | Открыть на 5 с; serving живёт только до границы freshness |
| Quota manager → Finance | Отдельный breaker служебного API | Аналогично Campaign | Не выдавать новые средства; использовать разрешённые остатки |

`CLOSED` пропускает запросы; `OPEN` быстро отказывает; `HALF_OPEN` допускает ограниченные пробы. После open-интервала — до трёх последовательных успешных проб, один probe in-flight; любая ошибка снова открывает breaker. При повторных циклах пауза растёт до 30 с. Для Redis probe проверяет не только соединение, но и разрешённую generation; успешный `PING` не доказывает корректность бюджетного состояния. Для Finance probe — чтение статуса, а не новый AllocateGrant.

Бизнес-no-bid, нехватка средств, ошибка входного запроса и запрет доступа не считаются транспортным отказом зависимости. Показатели breaker не объединяются между всеми DSP/шардами: проблема одной группы не должна выключать остальных. Числа требуют настройки по ошибкам и времени восстановления стенда.

Важно различать механизмы: [Envoy circuit breaking](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/circuit_breaking) ограничивает ресурсы; [outlier detection](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/outlier) временно исключает плохие upstream. Это не тот же автомат CLOSED/OPEN/HALF_OPEN, который реализуется в клиенте зависимости. Изоляция обеспечивается также отдельными пулами RTB и фоновых задач, очередями ограниченной длины и readiness.

## 5. Повторные попытки

Для повторяемых фоновых операций применяется full jitter:

`delay(n) = random(0, min(cap, base × 2^n))`, где `n=0` перед первым повтором.

Общий deadline операции и retry budget важнее числа попыток. Повторяется одна ответственная сторона, а не одновременно gateway, клиентская библиотека и consumer. При открытом breaker попытки не отправляются.

| Операция | Retry-политика |
|---|---|
| Bid request через gateway | 0 повторов, 0 hedging, без переключения на legacy после timeout |
| Redis FinalizeDecision в RTB | 0 транспортных повторов в текущем запросе; неизвестный результат → no-bid, удержание/сверка |
| GetManifest / GetGrantStatus | До 4 попыток суммарно, base 100 мс, cap 1 с, deadline каждой 300 мс, общий бюджет 2 с |
| AllocateGrant | До 4 попыток, те же backoff, deadline каждой 500 мс, общий бюджет 3 с; неизменный `allocation_request_id` |
| Загрузка снимка | До 3 попыток, base 500 мс, cap 5 с; общий бюджет определяется размером. Экземпляр не ready; можно продолжить фоновую сессию позже |
| Kafka producer Ingestion | Идемпотентные внутренние retries в пределах `delivery.timeout` 500 мс; HTTP budget endpoint 1 с. По исчерпании — временная ошибка, без ACK |
| Outbox publisher | Долговременные retries с base 200 мс, cap 30 с, alert по возрасту outbox; факт не теряется после исчерпания короткого цикла |
| Серверный callback партнёра | Предлагается base 500 мс, cap 30 с, окно до 24 ч, но реальные числа фиксируются с DSP; тот же business key при каждом повторе |
| Finance consumer | При transient DB error пауза/retry с base 200 мс, cap 30 с; offset не коммитится; неисправимый факт — карантин и сверка |

Для gRPC повторяются `UNAVAILABLE` и `DEADLINE_EXCEEDED` с безопасным ключом. HTTP 429 вне RTB учитывает `Retry-After`; 4xx валидации и авторизации не повторяются. В распределённой сети отсутствие ответа не означает отсутствие commit: AllocateGrant и финансовый consumer обязаны быть идемпотентны даже при малом числе retries.

## 6. Идемпотентность финансов

Транспортный `eventId` недостаточен: партнёр может заново прислать один факт с новым event ID. Основной business key — `(partner_id, partner_settlement_id, charge_kind)`. Если источник не даёт устойчивый settlement ID, для данного профиля согласуется `(partner_id, auction_id, imp_id, bid_id, charge_kind)` и гарантия «один billable на bid». При невозможности согласовать устойчивую идентичность автоматическое списание не запускается.

Дополнительно выбранный CPM-профиль допускает только один первоначальный debit на `(reservation_id, charge_kind)`; это отдельное уникальное ограничение ledger. Даже другое значение settlement ID не должно повторно списать тот же резерв. Refund/adjustment имеет отдельный тип и ссылается на уже существующую проводку.

В одной транзакции Finance:

1. Проверить подлинность нормализованного источника и reservation proof, валюту, grant и предельную сумму. При первом уведомлении создать состояние резерва по proof в пределах уже выделенной суммы; чужие таблицы/Redis не читать.
2. Зафиксировать inbox с уникальным business key и hash значимых полей. Не включать изменяемые `receivedAt`/traceId в этот hash.
3. Создать ровно одну ledger-проводку и изменить финансовое состояние резерва/grant.
4. Создать outbox `SettlementApplied`, затем commit. После него разрешён commit offset.

Дубликат с тем же содержимым — успешный no-op; тот же ключ с другой суммой/валютой — конфликт, карантин и сверка. Корректировки и возвраты — отдельные операции с уникальным adjustment ID и ссылкой на исходную проводку. Исправление исторической записи без следа запрещено.

Ключи проведённых финансовых фактов сохраняются столько же, сколько ledger для соответствующего периода; короткий TTL ответа API не удаляет защиту от повторного debit. Сроки аудита и хранения определяются отдельно. At-least-once в транспорте сочетается с однократным финансовым эффектом; сквозной exactly-once не заявляется.

## 7. Резервные стратегии

| Недоступность / деградация | Допустимый fallback | Запрещённое поведение |
|---|---|---|
| Campaign временно не отвечает | Последняя подтверждённая проекция, пока действует lease/freshness и не известен revoke | Читать общий PostgreSQL синхронно или держать устаревшие кампании бессрочно |
| Дополнительный scoring недоступен | Детерминированная базовая ставка из текущей разрешённой кампании; не выше её лимита и с обычным резервом | Универсальная платная ставка без кампании, разрешений и бюджета |
| Нет безопасного кандидата | No-bid | Случайный/устаревший креатив |
| Redis timeout / неопределённая generation | No-bid и заморозка затронутой квоты | Прочитать старый баланс и продолжить расходование |
| Finance недоступен | Уже выделенная квота до исчерпания и окончания разрешения | «Временно разрешить» перерасход |
| Kafka/consumer отстаёт | RTB только пока разрешены данные и безопасные резервы; далее no-bid | Освободить деньги по TTL из-за отсутствующего события |
| Analytics недоступна | RTB продолжается; отчёты показывают давность/недоступность | Перенаправить тяжёлый отчёт на финансовый primary |

Базовый алгоритм в пилоте уже детерминированный; отдельный ML scoring сервис специально не добавляется. Публичная house ad может быть fallback собственного Delivery как неоплачиваемый контент, но не считается bid-response DSP и не маскирует сбой Bidding.

[Sequence: отказ и восстановление](diagrams/sequence-failure.puml) показывает timeout резерва, технический no-bid, открытие breaker и безопасное возобновление после проверки generation.

## 8. Наблюдаемость и испытания

Сквозная корреляция: gateway request ID → OpenRTB request/bid ID → reservation → event → ledger; это поля структурированного журнала, а не высококардинальные labels Prometheus. Полные user/device данные и секреты в логах отсутствуют. Для расследования сохраняются версии кампании, правил, адаптера и generation без персональных признаков.

Отдельные сигналы: latency каждого этапа, число технических no-bid по причине, время ожидания пула, breaker transitions, Kafka lag/ISR, возраст outbox, свежесть проекций, сомнительные/замороженные квоты, конфликты идемпотентности. Loss browser pixel до durable ACK измеряется отдельно от confirmed-event loss.

Обязательные проверки: ответ потерян после Redis commit; первичный Redis сменился со старым снимком; дубли callback с тем же и другим payload; consumer упал после ledger commit; billable пришёл раньше win; потеря Campaign при остановке кампании; повтор AllocateGrant после timeout; отставший partition проекции; overload одновременно с техническим no-bid. Для каждого проверяются деньги, количество обязательств, своевременный ответ и отсутствие вызовов OLTP из RTB.
