# AS-IS: диагностика текущей архитектуры

## 1. Исходные данные и границы анализа

AdScale — действующая рекламная SaaS-платформа со следующими характеристиками

- Гибридный монолит на C++ / Go / Python / Node.js обслуживает аукционы, выдачу рекламы, события, финансы, аналитику и кабинет
- Все компоненты используют один PostgreSQL
- Кеша, брокера, реплик чтения и контейнеризации нет
- Развёртывание ручное, production-кластер один

Анализ основан на предоставленном PlantUML и описывает механизмы деградации перечисленные ниже:

| Показатель | Данные показателя | Проблема |
|---|---|---|
| Пиковая нагрузка | 15 000 bid requests/s | Уже нет запаса производительности |
| Текущее время ответа | P95 110–120 мс при требовании ≤ 100 мс | Нарушение есть до подключения партнёра |
| Интеграция через 3 месяца | +20%, всего 18 000 RPS | Оптимизации нужны до переключения трафика |
| SLA нового партнёра | Ответ ≤ 80 мс; штрафы за latency и downtime | Отдельный более строгий критерий приёмки |
| Цель через год | 50 000 RPS, SLA 99,9%, несколько регионов | Требуются независимое масштабирование и устранение общих отказов |


## 2. Основные потоки

1. **Аукцион:** DSP → Ad Server → Auction Engine → Delivery Service → ответ.
   - Ad Server синхронно читает данные таргетинга, Auction Engine — кампании и ставки.
   - Время ожидания БД попадает в пользовательское время ответа.
3. **Выдача и события:** пользователь → Delivery; Delivery → Statistics → PostgreSQL.
   - Нет буферизации.
   - Синхронность всей цепочки относительно bid-response не указана: если ответ ждёт записи статистики, это дополнительная задержка;
   - Даже при отделённом запросе запись конкурирует за ту же БД.
5. **Управление:** рекламодатель → кабинет → CRUD кампаний / Financial / Analytics
   - Общий PostgreSQL.
7. **Пополнение:** кабинет → платёжный шлюз.
   - Обработка callback, верификация платежа и идемпотентность на схеме не раскрыты (возможно пробел в описании).
     

## 3. Узкие места, риски и влияние

| Проблема | Механизм и влияние на latency | Риск для бизнеса | Приоритет / проверка |
|---|---|---|---|
| Синхронные чтения в Ad Server и Auction Engine | Ожидание подключения, запросов и диска входит в каждый аукцион; хвосты задержек распространяются на ответ | Проигрыш аукционов, штрафы | P0: трассы и планы наиболее частых SQL |
| OLTP, события и аналитика в одном PostgreSQL | Конкуренция за CPU, I/O, cache и соединения; события нагружают WAL и обслуживание таблиц | Деградация сразу нескольких функций | P0: IOPS, WAL, pool wait, CPU, temp files |
| Прямые записи каждого события | Нет сглаживания всплесков и пакетирования; торможение БД передаётся производителю | Потеря событий либо рост времени ответа - зависит от обработки ошибок | P0: число событий/с, транзакций/с, retries и ошибок |
| Тяжёлая аналитика на primary | Длительные сканы вытесняют рабочий набор, занимают I/O и CPU; длинные транзакции мешают очистке версий | Кабинет ухудшает обслуживание RTB | P0: длительность запросов и транзакций, query plans |
| Единственный PostgreSQL | Нет независимого узла для переключения при отказе | Остановка ставок, финансов, кабинета | P0: backup/restore, фактические RPO/RTO |
| Единая единица развёртывания и общие ресурсы | Нельзя отдельно масштабировать CPU аукциона и запись событий; ошибочный релиз затрагивает весь продукт | Общий простой и дорогой рост мощностей | P1: процессы, зависимости, ресурсные профили |
| Нет кеша / подготовленной модели чтения | Повторные чтения одного набора кампаний добавляют нагрузку; запрос зависит от доступности primary | Нет устойчивого резерва для +20% | P0: объём активных данных, частота изменений и hit-rate прототипа |
| Один production-кластер | Общая область отказа инфраструктуры | Недоступность всего продукта | P1: зоны размещения и общие зависимости неизвестны |
| Ручной deploy | Изменения трудно повторять, откат медленный, больше конфигурационных ошибок | Релизы повышают риск простоя | P1: длительность выкладки/отката и история инцидентов |
| Нет SRE | Неочевидны владельцы, скрытые зависимости и порядок восстановления | Срок восстановления растёт | P1: назначить владельцев и проверить runbooks |

Один production-кластер не обязательно означает один сервер, но один инстанс PostgreSQL — явная точка отказа.

## 4. Масштабирование

Не решит проблему, т.к. добавление копий монолита увеличивает число одновременных обращений к общей БД. Если ограничение находится в PostgreSQL, это может ускорить насыщение пулов и усилить очередь. Вертикальное расширение и SQL-оптимизация полезны как временные меры, но не разделяют конфликтующие нагрузки и не устраняют общую точку отказа.

Время ответа можно представить как сумму ожидания на входе, подбора кандидатов, ожидания и выполнения SQL, вычисления аукциона и подготовки ответа. При высокой утилизации рост очередей нелинеен: +20% запросов не означает ровно +20% latency. Нельзя вывести будущий P95 из текущего P95 умножением на 1,2. Значение свыше 150 мс из кейса — риск, а не проверенный прогноз.

Перцентили отдельных этапов также нельзя просто сложить и объявить итоговым P95: нужна сквозная трассировка. Размер пула нельзя оценить по формуле RPS × P95.

## 5. Что измерить до изменения архитектуры

| Проверка | Какой вопрос закрывает | Результат для проектирования |
|---|---|---|
| End-to-end трассы по DSP и типу запроса | Где расходуются 110–120 мс: очередь, CPU, БД или выдача? | Приоритет оптимизаций и бюджет этапов |
| Нагрузочный профиль 15k / 18k, реальные размеры и распределение кампаний | Какова точка насыщения, есть ли горячие кампании? | Базовая линия и требования к масштабированию |
| `pg_stat_statements`, планы SQL, locks, WAL и I/O | Какие запросы и операции ограничивают БД? | Индексы, лимиты аналитики, порядок выноса нагрузки |
| События/с отдельно от bid requests/s | Какой поток реально нужно буферизовать? | Число разделов брокера, retention, диски |
| Поток кампаний и бюджетов, модель тарификации | Насколько допустимы устаревшие данные? | Версии проекций, ограничения ставок, резервирование |
| Сбои и восстановление на стенде | Что происходит при потере БД, узла и сети? | RPO/RTO, сценарии деградации и runbooks |

До получения измерений приоритетом остаётся снятие общей нагрузки с БД и устранение её синхронных чтений в RTB. Если измерения покажут доминирование CPU или неэффективного алгоритма отбора, оптимизация алгоритма и профилирование выполняются вместе с выделением сервиса.

## 6. Вывод диагностики

Главный архитектурный риск — связанность критического аукциона с событиями, аналитикой и управлением через общие ресурсы и PostgreSQL. Требуются разделение потоков, подготовленные данные для ставок, управляемое резервирование бюджета, изоляция отказов и воспроизводимые релизы. Само переименование модулей в микросервисы этих свойств не создаёт.
