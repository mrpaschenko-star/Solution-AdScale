# TO-BE: целевая архитектура AdScale

## 1. Архитектурный подход

Выбран **Strangler Fig с постепенной декомпозицией по бизнес-контекстам**. Входной маршрутизатор постепенно переводит трафик со старого пути на новые сервисы. Оставшийся монолит становится модульным: явные интерфейсы, владельцы данных, запрет новых межмодульных обращений к таблицам. Это совместимые части одной стратегии, а не три взаимоисключающих стиля.

Первое независимое бизнес-приложение — Bidding Service, объединяющее приём RTB, подбор кандидатов и Auction Engine. Перед его переключением нужно разгрузить PostgreSQL, обеспечить наблюдаемость и безопасный откат. Сбор событий может быть вынесен технически раньше: это не меняет приоритета бизнес-декомпозиции.

| Вариант | Преимущества | Ограничения для AdScale | Вывод |
|---|---|---|---|
| Оставить монолит и увеличить серверы | Быстро, мало новых технологий | Общая БД и общий отказ сохраняются; нельзя эффективно масштабировать потоки отдельно | Временная мера, не стратегия на год |
| Только модульный монолит | Ясные границы, простые локальные транзакции, меньше эксплуатационных затрат | Независимые релизы и ресурсная изоляция RTB ограничены; не выполняет заданную годовую цель | Использовать для остатка системы на переходе |
| Полный rewrite на микросервисы | Свобода выбора границ и технологий | За три месяца высок риск потерять скрытые правила аукциона и денег; нет зрелой эксплуатации | Отклонить |
| Strangler Fig и поэтапное выделение | Проверяемый эффект каждого шага, ограниченный радиус ошибки, обратимое переключение | Временно работают два пути и нужны совместимые контракты | Выбранный подход, [ADR-001](adr/ADR-001-evolution-strategy.md) |

## 2. Промежуточная архитектура через три месяца

Схема: [TRANSITION-3M.puml](Diagrams/TRANSITION-3M.puml).

- L7 ingress маршрутизирует запрос в старый путь или новый Bidding по DSP/когорте. Новый Bidding масштабируется отдельно и использует локальную подготовленную модель кампаний и региональный Redis для атомарных резервов квот.
- Монолит сохраняет кабинет, управление кампаниями, финансы и выдачу. Аукционный код переиспользуется; его сложные правила не переписываются без необходимости.
- Сборщик событий записывает поток в Kafka. Worker пакетно сохраняет события в отдельное хранилище статистики; аналитика читает его и выделенную read replica для нужных данных кампаний. Запись событий и тяжёлые отчёты уходят с transactional primary.
- PostgreSQL получает standby с автоматическим переключением и проверяемые backup/PITR. Аналитическая replica отделена от standby, предназначенного для HA, и имеет лимиты запросов.
- Изменения кампаний и выделение финансовых квот публикуются из монолита через transactional outbox. Каждый факт фиксируется вместе с изменением исходных данных, затем доставляется повторяемым publisher.
- Для первой очереди статистики допустим отдельный PostgreSQL с партиционированием и пакетной записью. Его достаточность проверяется по events/s. Если этого недостаточно, ClickHouse вводится уже на этом этапе; перенос всех OLTP-данных ради него не нужен.
- CI/CD и контейнеры вводятся для новых сервисов. Перевод всего legacy и внедрение Kubernetes не являются условием первого подключения.

Три месяца не означают завершение микросервисной миграции или полноценный второй регион. Результат этапа — проверенные 18 000 RPS, критерии latency из Drivers.md, независимое масштабирование Bidding и изоляция событий/аналитики. Заявление «сервис не будет давать сбоев» переводится в проверяемые SLO, failover и контролируемую деградацию: абсолютное отсутствие отказов технически не гарантируется.

## 3. Целевая архитектура через год

Основная схема: [TO-BE.puml](Diagrams/TO-BE.puml). Она показывает логические приложения, владельцев данных и направления взаимодействий. Региональный serving-контур повторяется в двух регионах; узлы и зоны следует детализировать отдельной Deployment view в следующих заданиях.

### 3.1. Границы сервисов и данных

| Сервис / контейнер | Ответственность и причина границы | Собственные данные |
|---|---|---|
| **Bidding Service** | RTB-адаптеры, таргетинг, кандидаты, аукцион, резервирование ставки. Объединены ради малого числа сетевых переходов и общего профиля latency | Локальные неизменяемые read-модели; версионированные снимки в собственном object storage; региональный Redis с проекциями и резервами выделенных квот |
| **Campaign Service** | Кампании, ставки, таргетинг, статусы и настройки креативов; относительно редкие изменения | Campaign PostgreSQL и outbox; логическое хранилище креативов |
| **Finance Service** | Пополнения, ledger, квоты, счета и сверка; отдельная транзакционная граница денег | Finance PostgreSQL с журналом проводок, резервами, inbox/outbox и ключами идемпотентности |
| **Delivery Service** | HTML/JS и выдача креативов после результата аукциона; масштабируется по показам | Собственная производная модель выдачи в Redis; постоянные оригиналы принадлежат Campaign |
| **Event Ingestion Service** | Проверка, нормализация и устойчивый приём показов, кликов и win/loss/billing-уведомлений | Принадлежащие домену событий Kafka topics и архив событий в object storage; собственная SQL-БД не нужна |
| **Analytics Service** | Проекции, агрегации и API отчётов; отдельный профиль хранения/чтения | ClickHouse; replay из брокера/архива; дедупликация по business event ID |
| **Advertiser Dashboard / BFF** | UI, сессии и композиция ответов для кабинета. Не владеет кампаниями или балансами | Stateless; отдельная бизнес-БД не нужна |

«База на сервис» означает исключительное владение данными и доступом на запись, а не обязательную SQL-БД для каждого stateless-приложения. В годовой цели Campaign и Finance используют отдельные PostgreSQL-кластеры; Bidding и Delivery — отдельные Redis-пулы. Изолированные buckets/prefixes и topics имеют отдельные права и владельцев. Общая брокерная инфраструктура допустима с квотами ресурсов; аналитика не должна вытеснять финансовые события.

Ни один сервис не читает таблицы другого. Данные передаются через API, события и явно опубликованные снимки. Снимки и локальные копии — производные данные, их нельзя использовать как финансовый источник истины.

### 3.2. Инфраструктурные компоненты

- **Global routing и региональный RTB ingress:** health-based маршрутизация, TLS, защита от перегрузки, deadline и ограничения по партнёрам. Обычный management API Gateway не включён в RTB-путь.
- **API Gateway:** вход кабинета и управляющих API, аутентификация, rate limits, маршрутизация. Проверка прав на конкретную кампанию дополнительно выполняется сервисом-владельцем.
- **Kafka:** реплицируемый журнал с независимыми consumer groups для финансов, аналитики, проекций и архива. Данные кампаний/квоты и массовые события разделены по topics и квотам.
- **Redis:** подготовленные данные и атомарные операции над региональными квотами; отдельный кеш выдачи. Redis не заменяет финансовый ledger.
- **PostgreSQL HA:** отдельные OLTP-кластеры Campaign и Finance, standby и резервное копирование с проверкой восстановления.
- **ClickHouse:** аналитика событий и отчёты; репликация и резервные копии. Не используется для принятия решения о доступном бюджете.
- **Object storage и CDN:** версии креативов, опубликованные снимки, архив для replay; разделение прав и сроков хранения по назначению.
- **Наблюдаемость и доставка:** метрики, структурированные логи, выборочные трассы, CI/CD, canary, секреты вне кода, runbooks и дежурства. Инструменты могут быть managed; service mesh не обязателен.

### 3.3. Критический путь ставки

1. DSP → global routing → ближайший региональный ingress → Bidding. Адаптер проверяет запрос и оставшееся время.
2. Bidding подбирает кандидатов и рассчитывает ставку по локальной версионированной read-модели. Новая реплика не получает трафик до прогрева.
3. Bidding атомарно резервирует максимальную возможную стоимость обязательства в выделенной квоте через региональный Redis. Это один ограниченный сетевой этап; обращений в Finance/PostgreSQL и другой регион на запрос нет.
4. Возвращает bid-response с URL креатива или заранее подготовленной разметкой, либо своевременный no-bid. Если протокол требует `adm`, шаблоны подготавливаются заранее; отдельный синхронный вызов Delivery на каждый аукцион не нужен.
5. Просмотр креатива и фактические события идут отдельными HTTP-запросами в Delivery/CDN и Event Ingestion. Диагностическая телеметрия аукциона не блокирует ответ; обязательные финансовые факты обрабатываются устойчиво.

Предлагаемые окна, от приёма запроса AdScale до отправки ответа:

| Этап | Окно |
|---|---:|
| Ingress, проверки и диспетчеризация | 5 мс |
| Поиск кандидатов и таргетинг | 12 мс |
| Аукционные вычисления | 20 мс |
| Региональный резерв квоты | 6 мс |
| Сериализация ответа | 7 мс |
| Внутренний запас и ограниченное ожидание | 15 мс |
| **Внутренний deadline** | **65 мс** |

Оставшиеся 15 мс до 80 мс предназначены для сети и внешнего запаса. Это распределение deadline, не сумма перцентилей и не результат бенчмарка. На каждом этапе проверяется оставшееся время; при невозможности завершить безопасно возвращается no-bid. Неконтролируемую задержку интернета нельзя гарантированно ограничить архитектурой AdScale.

### 3.4. Кампании, бюджеты и финансы

**Кампании.** Campaign транзакционно изменяет данные и outbox. Publisher передаёт событие с идентификатором и монотонной версией. Bidding и Delivery обновляют свои проекции, игнорируют старые версии, замечают разрывы и восстанавливаются из снимка плюс последующих событий. Пока проекция неполна или слишком стара, затронутая кампания не участвует. Свежесть проверяется по обработанным watermark/heartbeat каждого нужного раздела: heartbeat не должен обгонять предшествующие изменения. Дата последнего изменения самой кампании для этого не подходит. Обычный TTL кеша не является механизмом гарантированного распространения изменений.

**Квоты.** Finance заранее выделяет ограниченные суммы кампании по регионам. В одной транзакции ledger блокирует выделенные деньги, поэтому сумма выданных квот не превышает доступный бюджет. Выдача и доставка квоты идемпотентны по `grant_id`; повтор события не увеличивает лимит. Bidding резервирует средства атомарно, до отправки ставки, с уникальным `auction_id` и верхней границей возможного списания. Если верхняя граница обязательства неизвестна, этот механизм применять нельзя до уточнения тарификации.

**Расчёт.** Авторитетное выигрышное/оплачиваемое событие ссылается на резерв. Finance одной транзакцией регистрирует факт в inbox, проводит списание и меняет соответствующий резерв. Повторный callback или replay не вызывает второе списание. Неиспользованная часть возвращается только по подтверждённому результату либо после согласованного окна окончательности. Тайм-аут HTTP сам по себе не доказывает проигрыш и не освобождает деньги.

**Неопределённость.** При сбое Redis возможна утрата последних резервов даже при репликации; нельзя считать старый снимок квоты достоверным. Новый epoch не получает остаток сомнительной квоты, старая квота целиком остаётся заблокированной в Finance до сверки. Старый владелец ограждается от трафика и права резервирования (fencing); при partition узел без действующей аренды не ставит. Новый регион получает лишь средства, которые не были выделены старому. Это сохраняет верхнюю границу расхода ценой недоступного бюджета и снижения fill rate.

Внутри обычной работы применяется атомарный резерв; после неопределённого failover — остановка затронутых кампаний, а не автоматическое восстановление денег из Redis. Конкретный протокол аренды, fencing и сверки требует отдельной спецификации и fault-injection тестов до production. Для первого этапа допускается ограничить квоты и число кампаний пилота, сохранив эти же инварианты.

**Пополнение.** Finance создаёт платёж у шлюза и проверяет подписанный callback либо серверный статус. Действие браузера не подтверждает зачисление. Ключи идемпотентности защищают от повторного платежного уведомления.

### 3.5. События и аналитика

Event Ingestion валидирует источник, формат и идентификатор, затем подтверждает событие после записи в Kafka с `acks=all`, replication factor 3 и `min.insync.replicas=2` в разных зонах; unclean leader election отключён. Конкретное размещение и настройки проверяются на отказе зоны. Доставка потребителям — at-least-once, финансовый эффект — идемпотентный. «Exactly once» для всей системы не заявляется.

В финансовом consumer запись inbox и проводка находятся в одной PostgreSQL-транзакции; offset подтверждается после неё. В аналитике нужен отдельный механизм дедупликации до публикации итоговых агрегатов: одна лишь фоновая дедупликация ClickHouse не гарантирует корректность произвольного `SUM` сразу после вставки.

При невозможности устойчивой записи producer получает ошибку и повторяет с тем же event ID. Для браузерных пикселей гарантировать повтор невозможно: отдельно измеряются доставленные и потерянные события. Если такое событие определяет списание, требуется подтверждаемая серверная доставка или договорённый механизм сверки с площадкой. Клиентский клик без проверки не становится финансовым фактом автоматически.

Неуспешные события повторяются с backoff и ограничением числа попыток; неисправимые сообщения попадают в DLQ с alert и процедурой повторной обработки. Финансовые ошибки не отбрасываются молча. При росте lag или отказе брокера резерв квот не освобождается преждевременно; по достижении лимита или опасной давности данных Bidding прекращает новые обязательства.

Производительность брокера считается по **events/s**, размеру и ключам событий. Пример для оценки, а не факт кейса: при 100 000 событий/с и 500 байтах/событие полезный поток составляет 50 MB/s, или 4,32 TB/сутки без сжатия. При трёх репликах это около 12,96 TB/сутки до накладных расходов. Поэтому retention выбирается по реальному профилю и допустимой длительности восстановления; долгий архив выносится в object storage. Партиционирование учитывает перекос кампаний, а не только средний RPS.

## 4. Масштабирование и мультирегиональность

**Serving — active-active.** Bidding, Delivery и Ingestion работают локально в двух регионах с независимыми Kafka и Redis. Кампании и выделенные квоты реплицируются асинхронно. Финансовые и campaign-записи имеют единственного активного владельца; второй регион содержит DR-копии. Эта схема не требует распределённой транзакции между регионами на каждый аукцион.

**Отказ региона.** Global routing прекращает отправку в нездоровый регион. Живой регион использует собственные квоты; перенос невыясненного остатка запрещён. Если Finance недоступен, расходуется только уже выданный запас. Автоматическое переключение его primary между регионами без fencing старого и проверки состояния запрещено, иначе возможен split-brain ledger.

**Мощность.** 50 000 RPS — суммарная годовая цель. При делении 25k + 25k потеря региона оставляет только 25k. Чтобы сохранить 50k при отказе, каждый регион должен иметь проверенную способность обслужить 50k с необходимым запасом, прогретыми данными и доступными финансовыми квотами. Холодный autoscaling не заменяет резерв. Если бюджет этого не допускает, документируется снижение пропускной способности при региональной аварии и отдельно согласуется SLA.

**Восстановление данных.** Репликация между регионами асинхронная, поэтому возможна потеря последнего хвоста подтверждённых только внутри погибшего региона событий. Нужны сохранённые ID, повторная доставка и сверка с партнёром. Цели RPO/RTO и ограничения приведены в Drivers.md. Нулевой RPO на полный отказ региона потребовал бы синхронного межрегионального подтверждения для критичных данных и иной оценки задержек/стоимости.

**Расчёт числа реплик.** По результатам теста определяется устойчивая мощность одной реплики `r` при целевом latency. Базовая оценка `N = ceil(целевой_RPS / (r × допустимая_доля_утилизации))`; дополнительно проверяются отказ реплики/зоны, скос по шардам и прогрев. Конкретное число машин без профиля нагрузки и теста не назначается.

## 5. Поведение при отказах

| Сбой | Поведение | Цена / защита |
|---|---|---|
| Недоступен Redis Bidding | Своевременный no-bid для затронутых кампаний; нет fallback в общий PostgreSQL | Падение fill rate без шторма запросов в БД |
| Устарела кампания / потеряна аренда | Приостановить ставки по кампании, восстановить проекцию | Предсказуемая граница устаревания |
| Недоступен Finance | Работать в рамках действующих квот, затем no-bid | Нет бесконтрольного расхода |
| Kafka не принимает события | Не подтверждать приём, включить retries/backpressure; ограничить новые обязательства | Недоступность части событий видна, потери не скрываются |
| Отстаёт Analytics | RTB продолжается; кабинет показывает давность отчёта | Финансовый ledger остаётся источником истины |
| Ошибка новой версии Bidding | Переключить совместимую когорту на проверенный путь | Возврат ограничен безопасной мощностью старого пути |
| Потерян регион | Перемаршрутизировать в живой, использовать только его безопасные квоты | Резерв ресурсов и ограниченная доступность control plane |

## 6. Этапы перехода и контроль риска

| Период | Изменения | Критерий завершения |
|---|---|---|
| Недели 1–2 | Восстановить карту зависимостей, добавить метрики/трассы, уточнить SLA; профилировать SQL и CPU; ограничить тяжёлые отчёты | Известны главные задержки, согласован профиль теста, есть базовая линия |
| Недели 3–5 | Event Ingestion + Kafka + пакетная запись отдельно; аналитическое чтение вне primary; HA и восстановление PostgreSQL | Сверены события, подтверждена разгрузка primary, отработан failover |
| Недели 6–9 | Bidding с переиспользованным алгоритмом, проекциями и квотами; независимый deploy; shadow без денежных эффектов | Совпадение бизнес-решений, безопасные бюджеты, целевой latency на стенде |
| Недели 10–12 | Canary по когортам, 18k-тест с DSP, fault injection и проверка отката | Выполнены условия запуска из Drivers.md |
| Месяцы 4–6 | Выделить Campaign и Finance с собственными данными; Delivery и аналитика ClickHouse | Нет межсервисного SQL, сверены деньги и отчёты |
| Месяцы 7–9 | Несколько DSP-адаптеров, второй регион, репликация, квоты и DR | Проверены partition, fencing, восстановление и маршрутизация |
| Месяцы 10–12 | Тест 50k, отказ региона, capacity/cost review, вывод legacy-пути | Подтверждены целевые SLO и владение эксплуатацией |

Это ориентир последовательности для выплнения проекта, а не обещание сроков без оценки команды. Если миграция финансов требует больше времени, граница сервиса вводится сначала внутри монолита, а выделение откладывается без ослабления денежных инвариантов.

**Смена владельца данных:** backfill из согласованного снимка → доставка изменений outbox/CDC → сверка → переключение единственного writer → запрет прежних записей. Нельзя независимо писать одно изменение в две БД без транзакционного механизма доставки. Изменения схемы проходят expand/contract; удаление старых полей — после завершения отката и сверки.

**Shadow и canary:** shadow вычисляет решения, но не отправляет ставки и не резервирует реальные деньги. Canary определяет единственного владельца реального запроса. На переходе старый и новый пути используют непересекающиеся бюджеты либо единый согласованный механизм квот; оба не должны расходовать полный баланс кампании независимо.

**Откат:** смена маршрута допустима до необратимого удаления старого контракта и только в пределах мощности старого пути. Если старый контур выдерживает 15k, нельзя вернуть в него все 18k: нужно снизить согласованный входящий объём, приостановить новый DSP или сохранить предыдущую стабильную версию Bidding. После переноса владения данными откат приложения не означает автоматический откат БД.

## 7. Эксплуатация, стоимость и остаточные риски

Для RTB, событий, финансов и общей платформы назначаются владельцы и заместители из команды. DevOps вместе с backend готовят дежурство, alerts по error budget, lag и квотам, а также короткие инструкции: отказ БД, отказ брокера, задержка проекций, сверка и rollback. Автомасштабирование учитывает latency, CPU, число in-flight запросов и lag, а не только средний CPU.

Для ограниченного бюджета предпочтительны managed PostgreSQL/Kafka, если они доступны и выгоднее по совокупной стоимости. До закупки сравниваются инфраструктура, трафик между регионами, хранение, дежурства и стоимость второго региона. Kubernetes, отдельный сервис каждого алгоритма и глобальная синхронная БД не вводятся без подтверждённой необходимости.

Основные оставшиеся риски: неизвестная семантика 80 мс, недооценённый поток событий, сложность безопасных квот, неполные знания о legacy и недостаток команды для эксплуатации. По каждому требуется проверка до соответствующего этапа запуска. Целевое видение задаёт направление и критерии, но не доказывает достижение 50 000 RPS без измерений.

## 8. Связь драйверов и решений

| Драйвер | Решение | Проверка |
|---|---|---|
| Q1, Q2: latency | Единый Bidding, локальные read-модели, региональный резерв, deadline | Совместный DSP-тест, распределение end-to-end latency |
| Q3: деньги | Ledger, квоты, inbox/outbox, fencing | Повторы, сбои и инварианты средств |

| Q10–Q12: безопасность, эксплуатация, стоимость | Владельцы данных, права, CI/CD, managed по TCO | Аудит доступа, runbooks, cost review |
