# Стратегия данных для каждого сервиса

## 1. Database per Service

| Сервис | Тип БД / хранилища через год | Авторитетные данные и обоснование |
|---|---|---|
| **Bidding** | Региональный Redis Cluster с репликами; локальный immutable индекс; версионированные снимки в object storage | Redis хранит решения, резервы и runtime выделенных grants: нужен короткий атомарный read-modify-write. Индекс кампаний производный. Redis не является бухгалтерским ledger; потеря резервов вызывает заморозку квот, а не восстановление полного остатка |
| **Campaign** | Отдельный PostgreSQL HA; object storage для креативов и снимков | Кампании, targeting, ссылки на креативы, статусы, правила ставок, версии и outbox. Транзакции, ограничения и optimistic locking упрощают согласованное управление. Бинарные креативы не хранятся в OLTP |
| **Statistics** | Kafka как оперативный журнал, object storage как долгосрочный архив | Владение приёмом, нормализацией, идентификаторами событий, архивными manifests и проверкой полноты. Поток append-only, пакетное хранение дешевле бесконечного роста PostgreSQL. Kafka имеет конечный retention и не заменяет архив |
| **Analytics** | ClickHouse: ReplicatedReplacingMergeTree и Distributed-представления | Собственные факты и агрегаты для отчётов. Колоночное чтение и сжатие подходят для больших временных диапазонов; масштабирование независимо от OLTP. Данные производные, восстанавливаются из архива и Kafka |
| **Finance** | Отдельный PostgreSQL HA | Ledger, grants, inbox, outbox, расчёты, счета и состояния сверки. ACID, уникальные ограничения и точное представление денег нужны сильнее, чем горизонтальная запись любой ценой |

- Кластер Kafka и object storage могут быть общей инфраструктурой, но topics, buckets/prefixes, права, ключи шифрования и retention имеют владельцев. 
- Analytics владеет своими таблицами и получает события по контракту.
- Statistics не пишет напрямую в ClickHouse Analytics.

Схема владения: [data-ownership](diagrams/data-ownership.puml).

В трёхмесячной версии Statistics Worker временно пишет в **отдельный Statistics PostgreSQL** пакетами, с партициями по дате события. Это снижает риск внедрения нескольких платформ одновременно. При переходе на ClickHouse Analytics выполняет backfill, сравнивает количества/суммы по tenant/date, догоняет события от checkpoint; затем переключаются отчёты. Statistics PostgreSQL становится read-only на согласованное окно отката и выводится из эксплуатации после проверки архива. Постоянная двойная запись двумя сервисами в одну таблицу не допускается.

## 2. Модели и инварианты

**Campaign:** `campaign(campaign_id, advertiser_id, version, status, targeting, bid_policy, creative_version)`, `creative`, `outbox`. Изменение кампании и событие пишутся одной транзакцией. Version монотонна внутри кампании. Денежный лимит в настройках — намерение рекламодателя; доступные для расхода деньги подтверждает только Finance.

**Finance:** `account`, неизменяемые `ledger_transaction`/`ledger_entry`, `grant`, `settlement`, `inbox`, `outbox`. Денежные значения — целые micros с валютой, без float; сумма дебетовых и кредитовых проводок равна в каждой валюте. Корректировка создаёт новую проводку со ссылкой на исходную. Выдача grant блокирует обеспеченные деньги под уникальным `allocation_request_id`.

Одна транзакция Finance фиксирует inbox, проводки, изменение grant и outbox. Уникальны `(partner_id, partner_settlement_id, charge_kind)` и `(reservation_id, charge_kind)` для первичного списания. Повтор с другим содержимым направляется на сверку. Финансовая дедупликация хранится столько же, сколько соответствующий ledger, и не удаляется через RTB TTL. Событие win само по себе не создаёт расход; в CPM-пилоте клики и технические показы также не являются вторым источником списаний.

**Bidding:** локальная `CampaignProjection`, `RequestDecision`, `GrantRuntime`, `BidReservation`. Для каждого grant `available + held + spent = allocated`. В Redis все ключи одной операции имеют общий hash tag логического serving-шарда. Finance не читает Redis: подтверждение резерва передаётся проверяемым `reservationProof`, связанным с grant, generation, валютой, верхней суммой и сроком окончательности. Правила описаны в [задании 2](../Task-2/bidding-service.md).

**Statistics:** immutable envelope, исходная и нормализованная формы, `event_id`, источник, `occurred_at`, `received_at`, schema version, регион и архивный диапазон offsets. События с персональными идентификаторами минимизируются и псевдонимизируются; секреты и полный bid request в аналитику не копируются. Сроки хранения псевдонимных рекламных событий и финансовых документов различны.

**Analytics:** tenant/date/event fact, версии измерений Campaign, подтверждённые финансовые факты и агрегаты. Отчёт за прошлый период использует версию кампании на момент события, а не текущий targeting. Баланс в кабинете запрашивается у Finance; аналитическая копия не авторитетна для списания.



## 3. RPO и RTO по типу отказа

RPO — утрата уже подтверждённых данных, RTO — время восстановления указанной функции от обнаружения отказа. Недоставленный клиентом callback не считается принятым событием. Нулевой RPO ниже условен: гарантируется лишь в заявленной модели **одного отказавшего узла/AZ**, при живом кворуме, корректном fencing и отсутствии общей порчи данных.

| Сервис | Узел / один AZ: RPO; RTO | Потеря региона: RPO; RTO | Условие восстановления |
|---|---|---|---|
| Bidding | Проекции: 0 авторитетных данных; runtime Redis может потерять хвост. Безопасный serving затронутого шарда ≤5 мин при наличии независимых средств | Проекции из источника/DR; runtime потерянного региона не переносится как достоверный. Serving ≤5 мин при тёплом втором регионе | Старые grants целиком остаются обеспеченными и замороженными до сверки. Без fencing, свежего индекса или новых квот RTO не гарантирован |
| Campaign | RPO 0 подтверждённых commits; запись ≤5 мин | Асинхронный DR: потеря до фактического lag, целевой lag ≤60 с, жёсткой верхней границы нет; управление ≤30 мин | Выбор согласованной timeline, новый writer epoch; сверка потерянных изменений с журналом. RTB не продолжает по бессрочно старой кампании |
| Statistics | RPO 0 событий с Kafka ACK; приём ≤5 мин | Потеря не скопированного хвоста; целевой lag ≤60 с, без гарантированного предела; приём ≤15 мин | DR-журнал/архив, позиции потребителей и дедупликация; источник повторяет неподтверждённое |
| Analytics | RPO 0 подтверждённых реплицированных вставок при insert quorum; свежесть зависит от consumer lag; отчёты ≤15 мин | Потеря копии восстанавливается до доступного источника; его RPO наследуется. Отчёты ≤4 ч для проверенного объёма restore | Snapshot + replay. Старые отчёты обозначаются stale; свежесть отдельно от доступности |
| Finance | RPO 0 подтверждённых commits; запись ≤5 мин | Асинхронный DR: хвост до фактического lag; целевой lag ≤60 с не гарантирует RPO ≤60 с; запись ≤1 ч после сверки | Ограждение старого writer, сверка с PSP/DSP, архивом и grants. Неясные обязательства блокируют средства |

Потеря Redis-резервов не равна разрешённой потере денег: Finance по-прежнему учитывает всю выделенную сумму как потенциальное обязательство. Нельзя обещать RPO 0 для самого runtime Redis на основании AOF или команды WAIT.

Для Campaign/Finance используются PostgreSQL primary и два standby в разных AZ, `synchronous_standby_names = 'ANY 1 (standby_b, standby_c)'`, `synchronous_commit = on`. Commit подтверждается после flush WAL локально и хотя бы на одном standby. HA-контроллер с кворумом продвигает только допустимого синхронного кандидата с сохранённым WAL и ограждает прежний primary. Если такого кандидата или кворума нет, запись останавливается; автоматического перехода на async ради доступности нет. Один async standby во втором регионе не создаёт RPO 0 при потере всего основного региона.

При региональном DR Finance нельзя просто открыть запись на копии с неизвестным хвостом: могли исчезнуть даже подтверждённые grants. До сверки система блокирует неизвестный расход целиком по затронутым счетам/регионам; выдача новых квот разрешена только из доказанно независимых средств. Старые региональные permits истекают и fenced, ledger восстанавливается/сверяется, затем выдаётся новая generation.

**SLA 99.9%:** за 30 дней бюджет простоя — 43,2 минуты, совокупно по всем инцидентам в области SLA. Предложенные региональные RTO Finance/Analytics не укладываются в общий платформенный SLA. Предлагается отдельно согласовать RTB SLA и SLO управления/отчётов. Если 99.9% обязателен для всех функций, нужны более быстрый проверенный DR, дополнительная мощность и бюджет; при требовании финансового RPO 0 между регионами — синхронная межрегиональная фиксация с измерением задержки и отказных режимов. Это ещё не реализованное свойство проекта.

## 4. Резервное копирование и восстановление

Реплика защищает от отказа оборудования; DELETE и логическая порча могут быстро попасть на все реплики. Резервные копии независимы от runtime-кластера, зашифрованы, проверяются по checksum, имеют отдельные права удаления. Ключи восстановления также должны быть доступны при потере региона.

| Данные | Политика — проектное предложение | Проверка восстановления |
|---|---|---|
| PostgreSQL Campaign/Finance | Полный backup еженедельно, differential ежедневно, непрерывный архив WAL с целевой доставкой ≤60 с; PITR 35 дней; копия в другом регионе/аккаунте, immutable retention | Ежемесячный restore в изолированную среду. Finance: баланс проводок, уникальность settlements, остатки и grants. Campaign: версии и outbox. Долгосрочный ledger-архив: предварительно 5 лет, срок требует юридического/договорного подтверждения |
| Креативы и снимки Campaign | Object versioning, checksum, межрегиональная копия; снимки каждые 15 мин, хранение 7 дней, последний проверенный снимок не удаляется до нового | Manifest включает consistent offsets именно регионального журнала, schema, SHA-256; replay не пропускает изменения |
| События Statistics | Непрерывный архив объектов с закрываемыми manifests по partition/offset; предварительно raw 30 дней, финансовые уведомления — по политике ledger | Проверка непрерывности offsets и количества событий; тест replay после истечения Kafka retention. Подробнее [Kafka](event-streaming.md) |
| ClickHouse | Ежедневный backup таблиц/метаданных в object storage, хранение 7 дней, копия в DR; канонические события и checkpoints сохранены для replay | Restore на заданном объёме + replay с перекрытием; dedup; сверка сумм и версий агрегатов. Retention фактов 30 дней, суточных обезличенных агрегатов 13 месяцев — рабочее предложение |
| Redis runtime | AOF `everysec`, RDB каждые 15 мин, 24 ч хранения для расследования; replica в другом AZ | Старое состояние не разрешает возобновить расходование. Только freeze/fencing/новая generation и сверка. Копия не заменяет ledger |
| Disposable cache | Без backup | Прогрев из владельца; ограничение параллелизма и readiness |

PITR и disaster restore имеют отдельные RTO от HA-переключения. Цель полного PITR Campaign ≤2 ч, Finance ≤4 ч **до сверки внешних обязательств**; итоговый срок Finance зависит от сверки и может быть больше. Эти цели измеряются на ожидаемом годовом объёме. Удаление архивов/бэкапов учитывает требования удаления персональных данных и допустимые сроки финансового хранения; бесконечный retention по умолчанию не применяется.

Ежеквартально проводится сценарий потери региона, ежемесячно — выборочный restore и сверка, перед интеграцией — полный rehearsal на репрезентативном объёме. Runbook хранит порядок восстановления: secrets/ключи и сеть → владельцы данных → Kafka/архив → проекции → выдача новых permits → canary трафика. Метрики: возраст последнего успешного backup, lag WAL/архива, фактические RPO/RTO, доля проверенных restore. Ответственность — backend-владельцы сервисов и DevOps; выделенного SRE в кейсе нет.

## 5. Соответствие 12-факторным приложениям

12 факторов описывают приложения; PostgreSQL, Kafka и Redis остаются stateful backing services. 

| Фактор | Применение в AdScale |
|---|---|
| Codebase | Версионируемые сервисы и миграции; один codebase сервиса, несколько развёртываний |
| Dependencies | Фиксированные версии клиентов/образов, воспроизводимая сборка |
| Config | Параметры окружения отдельно от образа; секреты доставляются защищённым механизмом, не попадают в код/логи. Для локальных материалов этой работы источник секретов только `~/secrets.env` |
| Backing services | БД/брокер/object storage доступны по конфигурации и отдельным credentials; контракт владельца сохраняется при смене инстанса |
| Build, release, run | Миграции expand/contract; release фиксирует код, schema compatibility и конфигурацию |
| Processes | Экземпляры приложения заменяемы; локальный индекс — восстановимая проекция, не единственная копия; ledger и offsets вне локального диска приложения |
| Port binding | Сервисы публикуют собственные HTTP/gRPC endpoints с health/readiness |
| Concurrency | Масштабирование процессами; consumer concurrency ограничена partitions; лимиты connection pools защищают БД |
| Disposability | SIGTERM прекращает приём, завершает ограниченный batch, фиксирует безопасные offsets; RTB draining; restart не освобождает деньги |
| Dev/prod parity | Одинаковые версии и семантика Kafka/PostgreSQL/Redis; тесты quorum, retries и failover на staging |
| Logs | Структурированный stdout, централизованный сбор, correlation IDs и редактирование чувствительных полей; ledger не заменяется логами |
| Admin processes | Backfill, repair и restore — отдельные версионируемые jobs с правами, аудитом и ограничением нагрузки |
