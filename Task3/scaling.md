# Репликация, шардирование и CQRS

## 1. Выбор по сервисам

Репликация копирует одни данные для доступности/чтения; шардирование распределяет разные данные для ёмкости/записи. Партиции PostgreSQL внутри одного сервера не увеличивают число независимых write-узлов.

| Сервис | Репликация / read replicas | Партиционирование и ключ шардирования | Почему |
|---|---|---|---|
| Bidding | Копии полного индекса в процессах; Redis primary + replica в другом AZ для каждого физического шарда | Логический serving-шард `H(partner_id, request_id)`, стабильная таблица маршрутизации; hash tag `{s17}` объединяет решение, grant и резерв | Дедупликация и резерв должны быть одной операцией; шард по request распределяет горячую кампанию. Grants заранее дробятся между шардами, деньги не копируются |
| Campaign | Primary + 2 standby в 3 AZ, минимум один synchronous ACK; отдельная async read replica только при измеренной нагрузке чтения | Сначала один primary; при исчерпании — `H(advertiser_id)` по каталогам tenants, все кампании рекламодателя вместе | CRUD не растёт линейно с bid RPS. Сначала индексы/пулы/реплики; ранний sharding увеличит стоимость миграций и отчётов |
| Statistics | Kafka RF=3, minISR=2, rack awareness по AZ; object storage с независимыми копиями | Kafka partitions по ключам из [таблицы топиков](event-streaming.md); архив `region/topic/date/hour/partition/offset-range` | Append-only поток распределён; события одного ключа упорядочены только в его partition. Временный PostgreSQL: дневные партиции по `occurred_at`, индекс `(advertiser_id, occurred_at)` |
| Analytics | По 2 ClickHouse replicas на shard в разных AZ; 3 Keeper в 3 AZ | Рабочий старт: 2 shards × 2 replicas; `cityHash64(advertiser_id, event_id)`; месячная partition по immutable `event_date` | Распределяет даже крупного рекламодателя; отчёты tenant требуют fan-out по shards. Реплики читают и подхватывают отказ, они не заменяют shard |
| Finance | Primary + 2 standby в 3 AZ с synchronous commit; отдельная async replica для некритичных выписок при необходимости | На первом этапе без sharding; ledger/inbox партиционировать по времени только с сохранением глобальной уникальности. Позже `account_id`/advertiser account | Транзакции счёта, grants и уникальные business keys должны находиться у одного владельца. RPS ставок не равен RPS ledger |

Для Finance временное партиционирование требует отдельного непартиционированного реестра бизнес-ключей или иной доказанной глобальной уникальности: `UNIQUE(key, date)` не предотвращает повтор с другой датой. До такой реализации inbox/реестр остаются непартиционированными. При шардировании финансов каждое событие маршрутизируется по проверенному account/grant, а не по данным клиента; переводы между счетами разных shards требуют отдельного протокола и не входят в CPM-пилот.

Снимок Campaign получают с согласованной позиции источника. Async replica не обслуживает проверку свежего бюджета, подтверждение собственной записи или critical manifest без доказанной позиции WAL. Кабинет после изменения читает primary либо ждёт нужную версию; устаревший replica read не выдаётся за подтверждение отмены кампании.

## 2. Аналитике нужны свои реплики

Через три месяца отчётность читает Statistics PostgreSQL; ограниченные отчёты по кампаниям могут использовать Campaign read replica со statement timeout, отдельным pool и лимитами. Реплика OLTP полезна как переходная разгрузка, но не решает стоимость исторических JOIN и объём событий. Длинные запросы на PostgreSQL standby могут конфликтовать с WAL replay; replica lag и отмены запросов контролируются.

Через год Analytics уже использует собственный ClickHouse, а не production PostgreSQL или Finance replica. Реплики ClickHouse нужны для чтения и HA: Distributed-таблица маршрутизирует чтение по одной актуальной replica каждого shard; отдельные query pools/лимиты памяти защищают ingestion. Вставка идёт синхронно в выбранный shard (без потери данных в локальной очереди Distributed), `insert_quorum=2` на двух replicas. Если вторая replica недоступна, чтение продолжается, ingestion этого shard приостанавливается, Kafka буферизует backlog. Возможная цена RPO 0 — снижение доступности записи аналитики. Async insert с ранним ACK без подтверждения flush здесь не используется.

Замена количества ClickHouse shards не должна направлять повтор прежнего `event_id` на другой shard: dedup локален таблице/shard. Используется версия маршрутизации, зафиксированная для event-time диапазона; расширение делается на границе новых диапазонов. Старые данные и replay сохраняют старый маршрут, либо выполняется полная контролируемая перекладка с проверкой дублей. Нельзя просто изменить modulo в producer и считать историю корректной.

## 3. CQRS — выборочно

| Контекст | Write-модель | Read-модель / свежесть |
|---|---|---|
| Campaign → Bidding | PostgreSQL + outbox | Immutable индекс Bidding, изменения P99 ≤5 с; нет подтверждённого watermark >10 с — затронутые кампании закрываются |
| Finance → serving | Ledger/grants PostgreSQL | Redis runtime использует только заранее заблокированные квоты; это делегированное право расхода, а не eventual-consistent копия баланса |
| Statistics → Analytics | Принятые события Kafka и архив | ClickHouse и агрегаты; рабочая цель свежести P95 ≤60 с при штатной нагрузке, лаг отображается в UI |
| Finance → отчёты | Подтверждённые ledger transactions | Analytics получает settlements; сведение/баланс остаются в Finance |

CQRS здесь отделяет пути изменения от чтения. Полный Event Sourcing для Campaign не нужен: PostgreSQL — источник истины, Kafka — журнал интеграции. Наличие outbox не делает Kafka единственным состоянием системы. Финансовый ledger неизменяем, но это также не требует переписывать все сервисы на Event Sourcing.

## 4. Мощность и ограничения

Исходные цели — 18 000 и 50 000 bid requests/s. Нагрузку событий и расчётов нужно измерять отдельно:

`events/s = bid_requests/s × bid_rate × win_rate × events_per_win + callbacks/retries/other_events`.

Это формула для оценки, а не утверждение о реальном профиле. Например, 100 000 событий/с по 500 B дают 50 MB/s, 4,32 TB/сутки логически и 12,96 TB/сутки при RF=3, до сжатия, индексов и служебных накладных расходов. 30 дней такого архива — 129,6 TB логически. Такой профиль может не соответствовать ограниченному бюджету; нужны реальные события/с, размер, компрессия и retention. Пример нельзя автоматически приравнивать к 50 000 RTB RPS.

Планирование включает CPU и память индекса Bidding, Redis операций/с и память резервов, broker disk/network, ClickHouse write amplification/merge backlog, IOPS и WAL Finance. Для 10 минут tombstones: 18 000 × 600 = 10,8 млн записей; при 50 000 — 30 млн. Даже 100 B/запись дают 1,08/3 GB без overhead, replicas и самих резервов; реальные размеры снимаются с образца ключей.

Если исправный primary Redis выдерживает `C` решений/с при требуемом P99 и целевой загрузке `u=0.6`, минимальная оценка физических shards — `ceil(RPS/(C×u))`. Значение C получают тестом именно `FinalizeDecision`, а не GET. Один логический shard с общим hash tag — один slot; для горизонтальной записи нужно достаточно логических shards. Свободную память закладывают под рост резервов, fork/AOF rewrite и отказ узла; приближение к лимиту при `noeviction` вызывает управляемый no-bid.

Для Kafka число partitions определяется максимумом требований к throughput и consumer parallelism. Стартовые значения в [event-streaming.md](event-streaming.md) — кандидаты на бенчмарк. При backlog `B` событий и producer rate `P`, consumer rate `C>P`, время догона не меньше `B/(C-P)`. Мощность recovery планируется с запасом сверх обычного приёма; если C≤P, увеличение retention лишь отложит потерю.

Read replicas не устраняют write bottleneck. До шардирования OLTP: индексы по реальным планам, уменьшение транзакций, отсутствие аналитики, batching событий, ограниченные connection pools и исправление hot rows. Finance масштабируется по частоте реальных billable-фактов и grants. Излишне маленькие grants снижают риск блокировки средств, но увеличивают нагрузку ledger и фрагментацию бюджета; размер подбирается по спросу и времени безопасного пополнения.

## 5. Регионы и изменение топологии

RTB работает active-active, но один аукцион имеет один home region. Gateway использует устойчивый affinity/региональный токен; повтор остаётся в исходном регионе и шарде. При недоступности home region повтор уже начатого запроса получает no-bid, а не новый резерв в другом регионе. Переключаются новые аукционы после fencing и подтверждения готовности. Региональная дедупликация без этой политики не обеспечивает глобальную уникальность.

Kafka и Redis обслуживают только локальный serving; межрегионального RTT в bid path нет. Campaign/Finance имеют одного активного писателя и async DR. События доставляются по регионам с сохранением версии; offsets региональных топиков различаются. Снимки привязаны к конкретному региональному журналу, числовые offsets между кластерами не копируются вслепую.

Для гарантированных 50 000 RPS после потери региона каждый выживший регион должен выдерживать весь поток и иметь свежие проекции/независимые квоты. Более дешёвый вариант — ограничение нагрузки и приоритетный трафик при отказе; это другая доступная мощность, которую нужно включить в договор. Для команды из 35 человек предпочтительны управляемые PostgreSQL/Kafka/object storage, если доступны нужные настройки и стоимость. Самостоятельные пять кластеров, Kubernetes и новый distributed SQL одновременно за три месяца не предлагаются.

Изменение Redis mapping проходит через drain старого replay-окна, запрет новых аукционов на старом mapping, сохранение маршрута повторов и явный перенос владельца. Grants/резервы остаются у старого владельца до финализации, либо переносятся согласованным протоколом с fencing. Онлайн-переназначение modulo без миграции может создать двойной резерв. Kafka partitions для ordered keys меняются через новый топик/версию маршрута с drain или согласованный cutover: рост числа partitions меняет распределение ключей.

Схема размещения находится тут: [data-replication](diagrams/data-replication.puml). Обещания RPO/RTO и backup-политика в [database-strategy.md](database-strategy.md).
