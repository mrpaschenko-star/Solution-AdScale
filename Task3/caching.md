# Кеширование 

## 1. Размещение и данные

В каждом RTB-регионе работают два **изолированных** Redis-контура: Bidding runtime и disposable cache. Они имеют разные лимиты памяти, credentials и политику eviction. Общий Redis для временного HTML и денежных резервов создаёт риск удаления обязательств под нагрузкой и не используется.

Основное чтение Bidding идёт из локальной immutable read-модели. Региональный runtime Redis размещён в той же сети, primary/replicas разнесены по AZ; межрегиональные обращения исключены. Атомарная операция резервирования имеет бюджет до 6 мс из общего внутреннего бюджета 65 мс, что требует измерения cross-AZ latency. Redis Cluster масштабирует запись; replica не обслуживает проверки бюджета, резервы или dedup, поскольку может отставать.

|---|---|---|---|

Disposable Redis использует `allkeys-lfu` с лимитом памяти. Runtime Redis — `noeviction`; отказ записи при переполнении превращается в no-bid и alert. Очистка завершённых резервов требует финального состояния, срока договорной сверки и сохранённой аудиторской записи. До согласования finality horizon численный TTL денежных резервов намеренно не назначается. Десятиминутный tombstone не ограничивает срок жизни обязательства.

Для удаления tombstones нужен подтверждённый replay horizon. Как в задании 2, предлагается аутентифицированный неизменяемый `X-Auction-Created-At`, ограничение возраста запроса и clock skew. Если партнёр не поддерживает это расширение, retention dedup должен покрыть весь договорной горизонт повторов. Нельзя распознать произвольно поздний повтор по удалённому ключу.

## 2. Инвалидация и согласованность

Изменение Campaign и outbox атомарны. Событие содержит `campaign_id` и `aggregate_version`; consumer применяет только ожидаемую следующую версию. Точный дубль игнорируется, конфликт той же версии или gap требуют восстановления. Обновление собирается вне критического пути и публикуется атомарной заменой указателя на индекс. Текущий запрос фиксирует одну версию модели, чтобы не смешать старый targeting и новую цену.

Инвалидация через Kafka надёжнее Redis Pub/Sub: после перезапуска можно дочитать журнал. Однако версия heartbeat должна подтверждать применение **всех предшествующих изменений соответствующей partition**, включая outbox backlog. Сам факт живого producer не доказывает актуальность. При отсутствии подтверждения более 10 с eligibility закрывается. Срочная остановка ограничена этой задержкой; мгновенная глобальная отмена не обещается.

В cache-aside есть гонка «инвалидация пришла, старое чтение вернулось позже». Поэтому значение записывается с version, сравниваемой с watermark/tombstone; ответ более старой версии не перезаписывает новый. TTL лишь ограничивает жизнь вторичного UI-кеша. В hot path просроченные разрешения на кампанию не продлеваются на основании TTL Redis.

Кешированные budgets не используются как источник доступных денег. `AllocateGrant` блокирует деньги в Finance до доставки в Bidding; повтор события выдачи не переинициализирует потраченный grant. Один `FinalizeDecision` проверяет dedup/fingerprint, generation/lease, сумму и атомарно записывает reserve+response. Ключи вида `decision:{s17}:…`, `grant:{s17}:…`, `reserve:{s17}:…` находятся в одном Redis slot. Cross-slot операция не считается атомарной.

## 3. Cache warming

1. Новый процесс Bidding ещё не ready. Получает manifest региона по служебному gRPC; скачивает immutable snapshot с SHA-256, schema version и consistent offsets.
2. Проверяет снимок, строит индекс в памяти. Producer снимка должен связать состояние с журналом через согласованный CDC/outbox checkpoint; чтение произвольного snapshot и затем Kafka `latest` недопустимо.
3. Дочитывает изменения от каждого checkpoint, проверяет непрерывность версий. Если нужный offset уже удалён retention, загружает новый снимок или доверенный архив; gap не пропускается.
4. Достигает свежего ordered watermark всех нужных partitions. Каждая полная реплика индекса имеет свою consumer group; общий group на все процессы ошибочно разделил бы обновления.
5. Проверяет действующую generation runtime, доступные grants и состояние маршрутизации. Выделение новых денег идёт через Finance, а не восстановление «полного остатка» из кеша.
6. Открывает readiness, принимает малую долю трафика. Последующие rolling updates прогреваются порциями, ограниченными object storage/network/CPU. Autoscaling запускается заранее: холодный процесс не может сразу принять RTB.

В disposable cache прогреваются только наиболее востребованные кампании и версии креативов; полное копирование всех исторических кампаний не нужно. Single-flight по ключу, небольшой фоновой concurrency, jitter TTL и ограниченный fallback pool предотвращают stampede. Для stale UI допустимо показать отметку времени; stale eligibility для аукциона недопустима.

## 4. Redis timeout и потеря primary

Timeout означает неизвестный исход атомарной операции: резерв мог сохраниться. Bidding возвращает технический no-bid и не создаёт второй reserve ID. При наличии времени возможна только проверка **того же** решения по установленному протоколу; автоматический повтор RTB отсутствует.

Redis AOF/репликация уменьшают потери, но async failover может вернуть старый остаток. Даже WAIT не превращает Redis в согласованный ledger. Поэтому протокол [cache-recovery](diagrams/cache-recovery.puml) обязателен:

1. При смене primary/replication identity или неопределённом состоянии затронутые shards закрываются, старая generation помечается `FROZEN`.
2. Recovery-контроллер ограждает старого владельца и primary сетевыми/инфраструктурными средствами, прекращает продление permits. Срок permits предлагается ≤10 с; учитывается ограниченная погрешность часов. Пока fencing/истечение не подтверждены, выдача новых разрешений запрещена.
3. Finance сохраняет старую сомнительную сумму заблокированной. Это консервативно снижает доступный бюджет, но не позволяет потратить его дважды.
4. Новый primary получает новую generation. Только независимо обеспеченные grants могут возобновить serving; восстановленный Redis snapshot не даёт права вернуть старые средства.
5. Подтверждённые notices, proof и ledger используются для сверки старых обязательств. Освобождение — по финансовой финализации/контракту, а не по отсутствию callback или истечению TTL.

Redis auto-failover без проверки generation не подойдёт этому проекту. Контроллер и клиент должны блокировать работу с новым primary до восстановления разрешений. Если такую интеграцию нельзя надёжно реализовать и проверить за три месяца, выпуск денежного RTB с этим механизмом блокируется; упрощать его до кеша баланса нельзя.

Метрики: возраст watermark, gap count, warm-up duration, cache hit ratio, Redis P95/P99, `rejected_connections`/ошибки записи, память и replica lag, frozen grants, сумма заблокированных средств и no-bid по причине. Alert должен предшествовать исчерпанию памяти/lease, а latency-тест учитывать AOF rewrite и отказ AZ.
